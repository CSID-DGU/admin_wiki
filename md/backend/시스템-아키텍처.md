# 시스템 아키텍처

코드 한 줄을 고치기 전에 그 코드가 전체 흐름의 어느 시점에서 호출되는지부터 알아야 합니다. Request가 신청부터 승인·거절·만료까지 어떤 상태를 거치는지, 그리고 회원가입·로그인·신청·승인·삭제·만료 각 단계에서 FE·BE·MySQL·Redis·Infra Server·Gmail·Slack이 어떤 순서로 통신하는지를 시퀀스 다이어그램으로 정리합니다. 세 가지 스케줄러(만료 처리, 사용자 수명주기, Slack 큐 Worker)의 동작 방식과 BE·FE 내부 패키지 구조도 함께 다룹니다.

## 1. Request 생명주기

사용자가 서버 사용을 신청하면 Request가 생성되고, 관리자 승인 여부와 컨테이너 운영 상태에 따라 아래 상태를 따라 전이됩니다. v2.0부터 승인은 **작업 등록**이라, PROCESSING은 "config-server 제어기가 계정·컨테이너를 만드는 중"을 뜻합니다.

```mermaid
flowchart LR
    PENDING -->|승인: 생성 작업 등록| PROCESSING -->|작업 성공| FULFILLED
    PROCESSING -->|작업 실패| PENDING
    PENDING -->|거절| DENIED
    FULFILLED -->|마이그레이션| MIGRATING -->|완료·건너뜀·실패| FULFILLED
    FULFILLED -->|만료·계정 삭제| EXPIRING -->|회수 성공| DELETED
    EXPIRING -->|회수 실패| FULFILLED
```

| 상태 | 설명 |
|------|------|
| `PENDING` | 신청 접수, 관리자 승인 대기 |
| `PROCESSING` | 생성 작업이 도는 중. 중복 승인도 막는다 |
| `FULFILLED` | 컨테이너 운영 중 |
| `MIGRATING` | 다른 노드로 옮기는 중 |
| `EXPIRING` | 컨테이너·계정 회수 중. 회수가 실패하면 FULFILLED로 돌아가 다시 시도할 수 있다 |
| `DENIED` | 관리자 거절 |
| `DELETED` | 회수 완료 |

오래 멈춘 PROCESSING·MIGRATING·EXPIRING은 5분마다 도는 재조정이 처리합니다(3절).

## 2. 전체 흐름

로그인부터 신청, 승인, 만료 처리까지 FE·BE·Infra Server 세 주체 간 통신 흐름입니다. 승인 과정에서는 Infra Server에 Ubuntu 계정 생성과 Pod 생성을 순서대로 요청하며, 하나라도 실패하면 이전 단계를 되돌리는 보상 트랜잭션이 실행됩니다. 만료 처리는 스케줄러가 매일 08:00에 자동으로 수행합니다.

### 회원가입

이메일 인증 후 회원가입 순서입니다. 인증번호는 Redis에 5분 TTL로 저장하고, 인증 완료 상태(`VERIFIED:{email}`)는 10분간 유지됩니다. 회원가입 시 이 키가 있는지 확인하고, 저장 후 삭제합니다.

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant Redis as Redis
    participant MySQL as MySQL
    participant Gmail as Gmail

    FE->>BE: POST /api/auth/email/send?email=...
    BE->>Redis: SET email:verify:{email} = 인증번호 (TTL 5분)
    BE->>Gmail: 인증번호 이메일 발송
    BE-->>FE: 200

    FE->>BE: POST /api/auth/email/verify?email=...&code=...
    BE->>Redis: GET email:verify:{email} → 코드 일치 확인
    BE->>Redis: DELETE email:verify:{email}
    BE->>Redis: SET VERIFIED:{email} = true (TTL 10분)
    BE-->>FE: 200

    FE->>BE: POST /api/auth/register {email, password, name, ...}
    BE->>Redis: VERIFIED:{email} 존재 확인
    BE->>MySQL: 이메일 중복 확인
    BE->>MySQL: INSERT user
    BE->>Redis: DELETE VERIFIED:{email}
    BE-->>FE: 201
```

### 로그인

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant Redis as Redis
    participant MySQL as MySQL

    FE->>BE: POST /api/auth/login {email, password}
    BE->>MySQL: 사용자 조회 및 비밀번호 검증
    BE->>Redis: SET RT:{userId} (7일 TTL)
```

JWT 토큰 구조, 재발급, 로그아웃 흐름의 상세는 [인증·보안](인증-보안.md)을 참고합니다.

```mermaid
sequenceDiagram
```

### 관리자 거절

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant MySQL as MySQL
    participant Gmail as Gmail

    FE->>BE: POST /api/admin/requests/{id}/rejection {adminComment}
    BE->>MySQL: UPDATE status=DENIED, adminComment
    BE->>Gmail: 거절 안내 이메일 (adminComment 포함)
    BE-->>FE: 200
```

이메일 발송은 try-catch로 감싸져 있어, 발송이 실패해도 거절 처리 자체는 그대로 완료됩니다. 실패 시 `AdminRequestCommandService`에 WARN 로그만 남습니다.

### 관리자 승인

승인은 생성 작업을 등록하고 바로 응답합니다. 계정·컨테이너 생성과 FULFILLED 확정은 뒤에서 일어납니다.

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant Poller as ProvisionJobPoller
    participant MySQL as MySQL
    participant Infra as config-server
    participant Gmail as Gmail

    FE->>BE: POST /api/admin/requests/{id}/approval {imageId, resourceGroupId, adminComment}
    Note over BE: PENDING → PROCESSING
    BE->>Infra: POST /operations/provision {request_id, username, account?}
    Infra-->>BE: 202
    BE-->>FE: 202 (PROCESSING)
    Note over Infra: 제어기가 계정 → 홈 → Kerberos → Pod → 포트 순으로 실행
    loop 3초마다
        Poller->>Infra: GET /operations/provision/{requestId}
    end
    Infra-->>Poller: SUCCESS + 만든 자원(uid, gid, pod, node, ports)
    Poller->>MySQL: FULFILLED, podName, uid/gid, 외부 포트 저장
    Poller->>Gmail: 컨테이너 배정 안내 (SSH·Jupyter 포트, 초기 비밀번호)
    Poller->>MySQL: 신청의 초기 비밀번호 삭제
```

화면은 승인 응답 뒤 신청 상태를 폴링해 결과를 판단하고, 진행 단계는 config-server의 `/requests/{requestId}/status`(프론트 nginx가 이 경로만 넘김)로 보여 줍니다. 작업이 실패하면 PENDING으로 돌아갑니다. 작업 방식의 상세는 [외부 연동](외부-연동.md)을 참고합니다.

### 마이그레이션

관리자가 컨테이너 상세에서 마이그레이션을 누르면 작업을 등록하고 바로 202로 돌아옵니다. 화면은 마지막 마이그레이션 결과를 3초마다 확인합니다.

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant Poller as MigrationJobPoller
    participant Infra as config-server

    FE->>BE: POST /api/admin/requests/{id}/migrations {nodes, force}
    Note over BE: FULFILLED → MIGRATING
    BE->>Infra: POST /operations/migrate {request_id, username, pod_name, nodes, force}
    BE-->>FE: 202
    Note over Infra: 노드 선택 → 새 Pod 생성·Ready → 기존 Pod 정리
    loop 3초마다
        Poller->>Infra: GET /operations/migrate/{id}
    end
    Poller->>BE: migrated면 새 Pod·노드·포트 저장, FULFILLED
    loop 3초마다
        FE->>BE: GET /api/admin/requests/{id}/migrations/latest
    end
```

홈 디렉터리는 유지되지만 컨테이너 안의 시스템 변경은 유지되지 않습니다. 새 포트가 배정되므로 사용자에게 새 접속 정보를 전달합니다.

### 변경 요청 (만료일 연장·그룹 변경 등)

FULFILLED 상태인 컨테이너에 대해 사용자가 만료일 연장, 그룹 변경, 볼륨 크기 변경 등을 요청할 수 있습니다. 변경 요청은 별도 ChangeRequest 테이블에 PENDING으로 저장되고, 관리자가 승인하면 원본 Request에 반영됩니다. 만료일 연장이 승인된 경우에만 이메일이 발송됩니다.

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant MySQL as MySQL
    participant Gmail as Gmail

    FE->>BE: POST /api/requests/{requestId}/change {changeType, newValue, reason}
    Note over BE: changeType: EXPIRES_AT / GROUP / VOLUME_SIZE / RESOURCE_GROUP / CONTAINER_IMAGE / PORT
    BE->>MySQL: INSERT ChangeRequest (status=PENDING)
    BE-->>FE: 201

    FE->>BE: POST /api/admin/change-requests/{id}/approval {adminComment}
    BE->>MySQL: ChangeRequest 조회 및 원본 Request 수정
    opt changeType = EXPIRES_AT
        BE->>Gmail: 만료일 연장 안내 이메일
    end
    BE->>MySQL: UPDATE ChangeRequest status=FULFILLED
    BE-->>FE: 200
```

변경 요청이 거절되는 경우(`POST /api/admin/change-requests/{id}/rejection`)에는 changeType과 무관하게 항상 거절 안내 이메일이 발송됩니다. 승인 흐름과 달리 EXPIRES_AT 조건이 없습니다.

### 관리자 수동 삭제

`DELETE /api/admin/users/{id}/ubuntu-account`는 그 사용자의 살아 있는 신청을 모두 회수하고 리눅스 계정까지 지웁니다. 비활성화는 `PATCH /api/admin/users/{id}` `{"active": false}`입니다. `DELETE /api/admin/users/{id}`(사용자 삭제)와 비활성화도 같은 정리 과정을 거칩니다.

```mermaid
sequenceDiagram
    participant FE as FE
    participant BE as BE
    participant MySQL as MySQL
    participant Infra as config-server

    FE->>BE: DELETE /api/admin/users/{id}/ubuntu-account
    loop 살아 있는 신청마다
        Note over BE: FULFILLED → EXPIRING
        BE->>Infra: POST /operations/revoke {request_id, pod_name}
        BE->>Infra: GET /operations/revoke/{requestId} (끝날 때까지)
        BE->>MySQL: DELETED
    end
    BE->>Infra: POST /operations/revoke {request_id, username, node_name, delete_account: true}
    BE->>Infra: GET /operations/revoke/{requestId} (끝날 때까지)
    BE-->>FE: 200
```

회수가 실패하면 신청을 FULFILLED로 되돌리고 오류를 돌려줍니다. 홈 디렉터리는 지우지 않습니다.

### 만료 처리 (매일 08:00 KST, 스케줄러)

만료 예고 이메일은 SETNX로 중복 발송을 막습니다. 스케줄러가 매일 실행되기 때문에, 같은 날 같은 사용자에게 D-7 이메일이 두 번 나가는 상황이 생길 수 있습니다. 발송 전에 `email:preexpiry:{id}:{dayLabel}:{date}` 키를 Redis에 SETNX로 쓰고, 이미 키가 존재하면 발송을 건너뜁니다. TTL은 25시간이라 하루가 지나면 자동으로 만료됩니다.

```mermaid
sequenceDiagram
    participant BE as BE
    participant Redis as Redis
    participant MySQL as MySQL
    participant Infra as Infra Server
    participant Gmail as Gmail
    participant Slack as Slack

    BE->>MySQL: 만료 D-7/3/1 Request 조회
    BE->>Redis: SETNX email:preexpiry:{id}:{dayLabel}:{date} (TTL 25h)
    Note over BE,Redis: 키가 이미 있으면 발송 건너뜀 (중복 방지)
    BE->>Gmail: 만료 예고 이메일
    BE->>Slack: 만료 예고 DM

    BE->>MySQL: expiresAt < now AND FULFILLED 조회
    BE->>Infra: 컨테이너 회수 작업 등록·완료 대기
    BE->>Infra: 계정 회수 작업 등록·완료 대기 (홈 보존)
    Note over BE: @Transactional → DELETED 저장 → AFTER_COMMIT
    BE->>MySQL: UPDATE status=DELETED
    BE->>Gmail: 삭제 완료 이메일
    BE->>Slack: 삭제 완료 알림 → #farm-admin / #lab-admin
```

## 3. 스케줄러

BE 내부에 세 가지 스케줄러가 상시 동작합니다.

| 스케줄러 | 실행 | 역할 |
|---------|------|------|
| `RequestSchedulerService` | 매일 08:00 | D-7/3/1 만료 예고 알림 발송, 만료된 Request 회수 |
| `RequestSchedulerService` (재조정) | 5분 간격 | 20분 넘게 멈춘 PROCESSING은 생성 작업이 없거나 실패했을 때만 PENDING으로, MIGRATING은 관리자 알림, EXPIRING은 회수 재확인 |
| `ProvisionJobPoller` | 3초 간격 | PROCESSING 신청의 생성 작업 결과를 조회해 FULFILLED 확정 또는 PENDING 복구 |
| `MigrationJobPoller` | 3초 간격 | MIGRATING 신청의 마이그레이션 작업 결과를 조회해 새 Pod 반영 또는 FULFILLED 복구 |
| `UserSchedulerService` | 매일 09:00 | 3개월 미접속 경고 → 비활성화(Soft Delete, 영구 보존) |
| `SlackNotificationWorker` | 1초 간격 | `slack:notification:queue`에서 메시지를 꺼내 Slack API로 발송, 최대 3회 재시도 |
| `InfraSlackNotificationWorker` | 1초 간격 | `slack:infra:notification:queue` 전용 Worker. 백엔드 알림 큐와 완전히 독립 운영, 최대 3회 재시도 |

### RequestSchedulerService

만료된 컨테이너를 삭제하는 흐름에서 주의할 점이 세 가지 있습니다.

첫째, 만료 대상 조회 시 `JOIN FETCH`로 User·ResourceGroup을 한 번에 가져옵니다. 단순 조회 후 알림 발송 단계에서 연관 엔티티를 건당 추가 조회하는 N+1 문제를 막기 위해서입니다.

둘째, 삭제 메서드 호출 시 같은 클래스 내에서 `this.delete()`로 호출하면 Spring AOP 프록시를 우회해 `@Transactional`이 적용되지 않습니다. 이를 피하기 위해 `@Transactional` 메서드를 별도 클래스(`RequestExpiryService`)로 분리하고, 해당 Bean을 주입받아 호출합니다.

셋째, 삭제 완료 알림은 `@TransactionalEventListener(phase = AFTER_COMMIT)`를 통해 DB 커밋이 확정된 후에만 발송됩니다. 트랜잭션이 롤백되면 이벤트도 함께 폐기되므로, DB에 반영되지 않은 삭제에 대한 알림이 발송되는 상황을 방지합니다.

```mermaid
sequenceDiagram
    participant Scheduler as RequestSchedulerService
    participant Expiry as RequestExpiryService
    participant Infra as Infra Server
    participant DB as MySQL
    participant Listener as EventListener

    Scheduler->>DB: 만료 Request 목록 조회 (JOIN FETCH)
    loop 만료된 Request마다
        Scheduler->>Expiry: deleteExpiredRequest(id)
        Note over Expiry: @Transactional 시작
        Expiry->>Infra: 컨테이너 회수 작업 (완료 대기)
        Expiry->>Infra: 계정 회수 작업 (완료 대기)
        Expiry->>DB: UPDATE status=DELETED
        Expiry->>Listener: 삭제 완료 이벤트 발행 (커밋 대기)
        alt 실패
            Note over Expiry: Rollback → 이벤트 폐기
            Scheduler->>Scheduler: 관리자에게 실패 알림
        else 성공
            Note over Expiry: Commit
            Listener->>Listener: AFTER_COMMIT — 이메일·Slack 발송
        end
    end
```

AFTER_COMMIT과 Self-Injection 패턴의 배경은 [핵심 설계 패턴](핵심-설계-패턴.md) 1·2번을 참고합니다.

### UserSchedulerService

사용자 수명주기를 관리합니다. 매일 09:00에 실행되며 두 단계를 처리합니다. 이전에는 Soft Delete 1년 경과 후 DB row를 완전히 삭제하는 Hard Delete 단계가 있었으나, 이력 보존을 위해 제거되었습니다. 비활성화된 계정은 Soft Delete 상태로 영구 보존됩니다.

**1단계 — 장기 미접속 경고**

마지막 로그인 시각(`lastLoginAt`)과 해당 사용자의 가장 최근 컨테이너 만료일(`expiresAt`) 중 더 늦은 날짜를 기준으로, 3개월(`INACTIVE_MONTHS=3`) 이상 경과한 활성 사용자(`isActive=true`)를 조회해 삭제 예고 이메일을 발송합니다. 컨테이너가 활성 상태라면 로그인이 없어도 삭제 대상에서 제외됩니다. 이 시점에서는 계정을 삭제하지 않고 경고만 합니다.

**2단계 — Soft Delete**

경고 이메일을 받은 사용자가 일정 기간(`NOTIFICATION_LEAD_DAYS=8`) 내에 로그인하지 않으면 계정을 비활성화합니다. `isActive=false`, `deletedAt=now()`로 설정하고 비활성화 이메일을 발송합니다. 이후 별도의 삭제 처리는 없습니다.

```mermaid
sequenceDiagram
    participant Scheduler as UserSchedulerService
    participant DB as MySQL
    participant Gmail as Gmail

    Scheduler->>DB: MAX(lastLoginAt, 최근 expiresAt) < now-3개월, isActive=true 조회
    loop 미접속 사용자마다
        Scheduler->>Gmail: 삭제 예고 이메일 (N일 후 삭제 예정)
    end

    Scheduler->>DB: 경고 후 NOTIFICATION_LEAD_DAYS 경과한 사용자 조회
    loop 대상 사용자마다
        Scheduler->>DB: isActive=false, deletedAt=now()
        Scheduler->>Gmail: 계정 비활성화 이메일
    end
```

각 사용자 처리는 독립 트랜잭션으로 실행됩니다(`UserLifecycleTransactionalService`에 위임). 특정 사용자 처리 실패가 다른 사용자 처리에 영향을 주지 않습니다.

### SlackNotificationWorker / InfraSlackNotificationWorker

승인, 삭제 등 비즈니스 로직이 Slack API 응답을 기다리며 블로킹되는 것을 막기 위해 Redis 큐를 사이에 둡니다. 알림이 발생하면 메시지를 큐에 즉시 적재하고, 전용 Worker가 1초마다 꺼내 Slack API를 호출합니다. 실패 시 최대 3회 재시도합니다.

구조는 생산자–소비자 관계입니다. 알림을 만드는 쪽(Service·Scheduler)은 생산자로서 큐에 메시지를 넣고 바로 다음 작업으로 넘어가고, Worker는 소비자로서 큐에 쌓인 순서대로 하나씩 꺼내 발송합니다. 양쪽이 서로를 기다리지 않으므로 Slack이 느리거나 장애가 나도 승인·삭제 처리 자체는 지연되지 않습니다.

일반 비즈니스 알림(`slack:notification:queue`)과 Infra 관련 알림(`slack:infra:notification:queue`)은 큐뿐 아니라 이를 소비하는 Worker 클래스(`SlackNotificationWorker`, `InfraSlackNotificationWorker`)도 완전히 분리되어 있습니다. 한쪽 큐가 밀려도 다른 쪽 발송에는 영향을 주지 않습니다.

1초 간격으로 설정한 이유는 Slack Webhook API의 rate limit이 채널당 초당 1건이기 때문입니다. 더 빠르게 폴링하면 제한에 걸려 메시지가 누락될 수 있습니다.

Redis List의 `RPUSH`(오른쪽 삽입)로 넣고 `LPOP`(왼쪽 꺼내기)으로 꺼내 FIFO 순서를 유지합니다. 큐에 테스트 메시지를 직접 넣어보고 Worker가 꺼내가는 과정을 `MONITOR`로 관찰하는 방법은 [Redis 키 카탈로그](Redis-키-카탈로그.md) 4번에 정리되어 있습니다. 처음 보는 사람은 이 절차를 한 번 따라 해보면 큐 동작을 눈으로 확인할 수 있습니다.

```mermaid
flowchart LR
    A["알림 발생\n(Service / Scheduler)"] -->|RPUSH| B[("slack:notification:queue\n(Redis List)")]
    B -->|LPOP, 1초 간격| C["SlackNotificationWorker"]
    C --> D{Slack API}
    D -->|실패, 최대 3회 재시도| C
    D -->|성공| E[완료]
```

## 4. 내부 구조 및 통신

FE는 화면(pages)과 API 클라이언트(services)로 나뉩니다. BE는 도메인별 패키지로 구성되며 각각 Controller → Service → Repository 레이어를 따릅니다. Infra Server는 K8s 클러스터 내부 서비스로 Ubuntu 계정과 Docker 컨테이너 생성·삭제를 담당하며, BE에서만 접근합니다.

### BE 도메인 구조

```
domain/
├── requests        — 신청 접수, 승인/거절, 변경 요청 처리
├── users           — 사용자 관리, 인증
├── groups          — Ubuntu 그룹(GID) 관리
├── alarm           — 이메일·Slack 알림 발송

├── monitoring      — Prometheus 메트릭 조회

```

### Infra Server API

K8s 클러스터 내부 서비스(`containerssh-config-service`)로 BE에서만 접근합니다. 서비스 이름에 `containerssh`가 남아 있으나 ContainerSSH 제품이 아니라 자체 개발한 서버입니다. 모든 호출에 내부 API 토큰(`X-Internal-Token`)을 붙입니다.

| 엔드포인트 | 역할 |
|-----------|------|
| `POST /operations/provision` | 계정(선택)·컨테이너 생성 작업 등록 (202) |
| `POST /operations/revoke` | 컨테이너 회수, `delete_account`면 계정 회수까지 작업 등록 (202) |
| `GET /operations/{kind}/{requestId}` | 작업 결과 (phase, 만든 자원) |
| `GET /operations/{kind}/{requestId}/steps` | 작업 단계 기록 |
| `POST /operations/migrate` | 다른 노드로 옮기기 작업 등록 (202) |
| `DELETE /pods/{name}` | 신청 없는 고아 Pod 삭제 (동기) |
| `POST /groups`, `POST /users/{u}/groups` | 그룹 생성, 사용자 그룹 추가 |

WebClient 설정·작업 결과 처리 상세는 [외부 연동](외부-연동.md)을 참고합니다.

## 5. 도메인 설명

BE는 아래 도메인으로 구성됩니다. 각 도메인의 엔티티 구조, 생명주기, 비즈니스 규칙 상세는 [도메인 설명](도메인-설명.md)을 참고합니다.

| 도메인 | 역할 |
|--------|------|
| `users` | 사용자 계정 관리, 인증. USER / ADMIN 역할 구분 |
| `requests` | 서버 사용 신청 접수·승인·거절. ChangeRequest(변경 요청) 포함 |
| `groups` | Ubuntu 그룹(GID) 관리 |
| `alarm` | 이메일·Slack 알림 단일 진입점. 이메일 중복 방지(SETNX), Redis 큐 연계 |
| `scheduler` | 만료 Request 처리(08:00), 사용자 수명주기(09:00), Slack 큐 소비(1초 간격) |
| `pod` | Pod 정보 및 외부 포트(SSH·Jupyter) 관리 |
| `containerImage` | 컨테이너 이미지 목록 관리 |
| `resourceGroups` | FARM / LAB 서버 풀 관리 |
| `monitoring` | Prometheus 메트릭 조회 |
| `messageTemplate` | 알림 메시지 템플릿 관리. messages.properties 기본값 + DB 오버라이드 |

## 6. Redis 키 사용 현황

BE는 7개의 Redis 키 패턴을 사용합니다.

| 키 패턴 | 타입 | TTL | 목적 |
|---------|------|-----|------|
| `email:verify:{email}` | String | 5분 | 이메일 인증번호 임시 저장 |
| `VERIFIED:{email}` | String | 10분 | 인증 완료 상태. 이 키가 없으면 회원가입 불가 |
| `RT:{userId}` | String | 7일 | Refresh Token. 이 키가 없으면 로그아웃 상태 |
| `email:preexpiry:{requestId}:{dayLabel}:{date}` | String | 25시간 | 만료 예고 이메일 중복 발송 방지 (SETNX) |
| `slack:notification:queue` | List | 없음 | Slack 알림 FIFO 큐 (1초 간격 소비) |
| `slack:infra:notification:queue` | List | 없음 | Infra 관련 Slack 알림 전용 큐 |
| `slack:cache:users:list` | String | 1시간 | 이메일 → Slack UserId 변환용 멤버 목록 캐시 |

키 패턴별 상세 설명(저장·삭제 시점, 값 형태, redis-cli 확인 명령)은 [Redis 키 카탈로그](Redis-키-카탈로그.md)를 참고합니다.
