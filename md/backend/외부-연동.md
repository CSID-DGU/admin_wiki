# 외부 연동

Admin BE는 계정을 만들거나 컨테이너를 띄우는 일을 스스로 하지 않고 config-server에 맡깁니다. 이 문서는 그 경계에서 무엇을 주고받는지, 그리고 경계 너머가 실패했을 때 Admin BE가 자기 기록을 어떻게 지키는지를 다룹니다. Slack·메일·Prometheus 등 나머지 연동도 뒤에 정리합니다.

## 한눈에 보기

| 상대 | 무엇을 | 방식 |
| --- | --- | --- |
| config-server | 계정·컨테이너·포트·그룹·비밀번호 작업 | 작업 등록 후 결과 조회 |
| Kubernetes API | Pod 상태·로그·이벤트 | 직접 읽기 (읽기 전용) |
| Slack | 관리자 채널 알림, 사용자 DM | Redis 대기열을 거쳐 전송 |
| 메일 서버 | 사용자 안내 메일 | SMTP |
| Prometheus | GPU 사용률, 컨테이너 수 | 조회 |
| Google Sheets | 발급 내역 옮겨 적기 | 운영 스택에서만 |

## 1. config-server

### 공통

| 항목 | 내용 |
| --- | --- |
| 주소 | 설정의 `config.base-url` (클러스터 내부 주소) |
| 인증 | 모든 호출에 `X-Internal-Token` 헤더 (`config.api-token`) |
| 호출 창구 | `JobClient` 인터페이스. 구현은 `ConfigServerJobClient` |
| 제한 시간 | 일반 호출은 `config.timeout-seconds`, 고아 Pod 삭제는 `config.pod-timeout-seconds`(기본 300초) |

서비스 코드는 config-server의 주소나 경로를 직접 알지 못하고 `JobClient`만 부릅니다. API 전체 명세는 [Infra API 레퍼런스](../infra/operations/API-레퍼런스.md)를 봅니다.

### 작업 종류

| 종류 | 등록 경로 | 무엇을 하나 | 식별 번호 |
| --- | --- | --- | --- |
| 생성 | `POST /operations/provision` | 계정(없으면)과 컨테이너, 접속 포트를 만든다 | 신청 번호 |
| 이동·재시작 | `POST /operations/migrate` | 새 Pod를 만들고 준비되면 기존 Pod를 지운다 | 신청 번호 |
| 회수 | `POST /operations/revoke` | 컨테이너를 지운다. `delete_account`면 리눅스 계정까지 | 신청 번호 |
| 비밀번호 | `POST /operations/password` | 계정과 떠 있는 컨테이너의 비밀번호를 바꾼다 | 비밀번호 재설정 번호 |
| 그룹 | `POST /operations/group` | 계정을 그룹에 넣거나 뺀다 | 그룹 작업 번호 |
| 포트 | `POST /operations/port` | 컨테이너를 다시 만들지 않고 포트를 열고 닫는다 | 포트 작업 번호 |
| 접속 차단·해제 | `POST /operations/access` | 계정의 모든 접속 포트를 막거나 연다 | 접속 작업 번호 |
| 홈 삭제 | `POST /operations/home` | 보존 기간이 지난 홈 폴더를 지운다 | 홈 정리 번호 |

결과는 종류와 식별 번호로 조회합니다.

| 경로 | 내용 |
| --- | --- |
| `GET /operations/{종류}/{번호}` | 작업 결과 |
| `GET /operations/{종류}/{번호}/steps` | 단계별 기록 (관리자 화면의 타임라인) |
| `GET /requests/{번호}/status` | 생성이 지금 어느 단계인지 |

### 결과 읽는 법

결과의 `phase` 값에 따라 처리합니다.

| `phase` | 뜻 | Admin BE의 처리 |
| --- | --- | --- |
| `none` | 등록된 작업이 없다 | 다음 바퀴에 다시. 오래 이 상태면 재조정이 판단 |
| `START` · `RETRY` | 진행 중 | 다음 바퀴에 다시 |
| `SUCCESS` | 성공 | 결과를 DB에 반영 |
| `FAIL` | 실패. 남은 자원 없음 | 직전 상태로 되돌리고 알림 |
| `FAIL` + `DEGRADED` | 실패했는데 자원이 남음 | **상태를 그대로 두고** 한 번 알림 |
| `UNKNOWN` | 결과를 알 수 없음 | **상태를 그대로 두고** 한 번 알림 |

결과를 읽는 규칙은 `JobResults` 한 곳에 모여 있습니다. 폴러·재조정·등록 실패 처리가 모두 같은 규칙을 씁니다.

!!! warning "이번 작업의 결과인지 확인한다"
    결과는 번호로만 조회되므로, 같은 신청의 **이전 작업** 결과가 보일 수 있습니다. 등록할 때 받은 작업 번호(`jobId`)와 결과의 작업 번호가 다르면 반영하지 않습니다. 이 확인을 빼면, 다시 승인한 신청이 예전 실패 결과를 읽고 곧바로 되돌아갑니다.

### 등록이 실패로 보일 때

등록 요청이 실패로 보여도 작업이 등록됐을 수 있습니다.

| 상황 | 처리 |
| --- | --- |
| 요청이 닿지도 못했다 (연결 거부) | 등록되지 않은 것이 확실하므로 되돌린다 |
| config-server가 답으로 거절했다 (4xx) | 되돌리고 사유를 돌려준다 |
| 같은 번호의 작업이 이미 돌고 있다 (409) | 새로 등록하지 않고 그 작업의 결과를 기다린다 |
| 답을 받지 못했다 (시간 초과, 연결 끊김) | **등록되지 않았다고 단정하지 않는다.** 결과를 조회해 작업이 있으면 그대로 진행한다 |

마지막 경우가 `JobRegistrationUnconfirmedException`입니다. 이때 되돌리면, 실제로는 등록돼 도는 작업이 만든 컨테이너를 가리키는 신청이 없어집니다.

### 오류 코드로 바꾸기

| config-server의 응답 | Admin BE의 오류 |
| --- | --- |
| 요청 내용 때문에 거절 (4xx) | 422 `INFRA_REQUEST_REJECTED` |
| 서버 오류 (5xx), 연결 실패 | 502, 호출 목적별 코드 (`POD_CREATION_FAILED` 등) |
| 같은 작업이 진행 중 (409) | 409 `INVALID_REQUEST_STATUS` 등 |

4xx와 5xx를 구분해 주어야 화면에서 "요청이 잘못됐는지, 서버에 문제가 있는지"를 가릴 수 있습니다. config-server의 응답 본문은 로그와 오류 메시지에 남습니다.

### 생성 작업의 내용

승인하면 다음을 담아 등록합니다.

- 신청 번호, 계정 이름, 서버 이름
- 계정을 새로 만들어야 하면 계정 정보: 리눅스용 비밀번호 해시, 표시 이름, 그룹
- 예전에 받은 계정 번호가 있으면 그 번호 (같은 번호로 되살리기 위해)

계정이 이미 살아 있으면 계정 정보를 빼고 보내 컨테이너만 만들게 합니다.

성공 결과로 계정 번호(UID/GID), Pod 이름, 노드, 포트 목록, 새로 만든 그룹의 번호를 받아 DB에 반영합니다.

### 회수 작업의 내용

| 호출 | 지우는 것 |
| --- | --- |
| 컨테이너 회수 (`delete_account=false`) | 컨테이너와 접속 포트 |
| 계정 회수 (`delete_account=true`, 노드 이름 포함) | 그 노드의 리눅스 계정. **홈 폴더는 남긴다** |

- 이미 없는 것을 지우라는 작업은 성공으로 끝납니다. 그래서 다시 시도해도 안전합니다.
- 계정 회수에는 **노드 이름을 반드시** 넘깁니다. 노드를 모르면 config-server가 회수를 보류합니다. 모든 노드를 훑으면 이름만 같은 무관한 옛 계정까지 지울 수 있기 때문입니다.
- 계정은 그 사용자가 컨테이너를 썼던 노드마다 따로 회수합니다.

### 작업이 아닌 호출

| 호출 | 용도 |
| --- | --- |
| `DELETE /pods/{이름}` | 신청 기록이 없는 Pod를 지운다. 신청이 있는 Pod면 409 |
| `GET /reserved-names` | 쓸 수 없는 계정 이름 목록 (10분마다 받아 둠) |

### config-server가 Admin BE를 부르는 경로

config-server는 컨테이너를 만들 때 신청 내용(이미지, 후보 노드, 추가 포트, 그룹)을 Admin BE에서 다시 읽습니다.

| 경로 | 용도 |
| --- | --- |
| `GET /api/requests/config/by-request/{신청 번호}` | 생성·이동 작업이 신청 내용을 읽는다 |
| `POST /api/internal/slack/notify` | 인프라 쪽 알림을 Slack으로 보낸다 |

둘 다 내부 토큰으로만 열립니다([인증·보안](인증-보안.md) 6절).

### 책임의 경계

| Admin BE가 하는 일 | Admin BE가 하지 않는 일 |
| --- | --- |
| 무엇을 해도 되는지 판단 | 계정·컨테이너를 직접 만들고 지우기 |
| 작업 등록과 결과 반영 | 작업을 단계별로 실행하고 재시도하기 |
| 결과에 따른 상태 이동과 알림 | 실제 자원과 기록이 어긋났는지 판정하기 |

"기록에는 있는데 실제로는 없는 컨테이너" 같은 어긋남을 찾아 판정하는 일은 Admin BE의 몫이 아닙니다. Admin BE는 어긋남이 생기지 않도록 원인을 막는 데까지만 합니다.

## 2. Kubernetes API

관리자 화면의 Pod 목록·상세·로그·이벤트는 Admin BE가 쿠버네티스 API로 직접 읽습니다(`PodQueryService`). 권한은 **자기 스택의 네임스페이스 안 읽기**뿐입니다.

- 조회 대상 네임스페이스는 설정의 `kubernetes.pod-namespace`입니다.
- 권한이 빠지면 조용히 빈 값이 나오기 쉬워서, 실패하면 어떤 조회가 왜 실패했는지 로그에 남깁니다.
- 멈춘 컨테이너 감시(`ContainerStopWatcher`)도 이 조회를 씁니다.

## 3. Slack

보내는 방법은 세 가지입니다.

| 방법 | 쓰는 곳 | 필요한 설정 |
| --- | --- | --- |
| 웹훅 | 채널에 글 올리기 | `slack-webhook-url.<채널 키>` |
| 봇으로 채널에 올리기 | 신청서 알림. 이후 진행을 **같은 메시지의 댓글**로 달 수 있다 | `slack.bot-token`, `slack-channel-id.<채널 키>`, 봇을 그 채널에 초대 |
| 봇으로 DM | 사용자 개인 안내 | `slack.bot-token` |

- 봇으로 올리지 못하면(채널 ID가 없거나 봇이 채널에 없음) 웹훅으로 대신 보냅니다.
- DM은 사용자의 이메일로 Slack 회원을 찾아 보냅니다. 학교 이메일과 "자주 사용하는 이메일"을 모두 봅니다. 회원 목록은 1시간 동안 Redis에 보관합니다.
- 모든 전송은 Redis 대기열을 거칩니다([핵심 설계 패턴](핵심-설계-패턴.md) 9번).

서버(LAB·FARM)마다 다른 채널은 설정의 `app.servers.<서버 이름>`에 있습니다.

```yml
app:
  servers:
    FARM:
      public-host: <사용자에게 안내할 접속 주소>
      admin-channel: farm-admin        # slack-webhook-url.farm-admin
      request-channel: farm-request    # 신청서 채널. 생략하면 admin-channel
```

### Slack 가입 확인

승인·만료 안내가 Slack DM으로 가므로, 운영에서는 신청을 받기 전에 신청자가 Slack 워크스페이스 회원인지 확인합니다(`slack.membership-check.enabled`). 이름과 이메일이 모두 맞아야 같은 사람으로 봅니다. Slack에 닿지 못하면 **통과시킵니다.** Slack 장애가 신청 장애로 번지면 안 되기 때문입니다.

## 4. 메일

SMTP로 보냅니다(`spring.mail.*`).

- 문구는 `messages.properties`에 있고, 관리자가 화면에서 고친 값이 있으면 그것을 씁니다.
- 연결·전송 제한 시간이 코드 기본값으로 걸려 있습니다. 메일 서버가 멈춰도 요청과 예약 작업이 함께 멈추지 않습니다.
- 발송이 실패하면 기록하고 관리자에게 알리되, **본래 처리는 실패로 만들지 않습니다.**

## 5. Prometheus

대시보드의 지표를 조회합니다(`GET /api/monitoring/metrics`, 로그인 필요). 주소는 `prometheus.base-url`입니다.

| 지표 | 쿼리 |
| --- | --- |
| 서버별 평균 GPU 사용률 | `avg by(Hostname)(DCGM_FI_DEV_GPU_UTIL)` |
| 서버별 GPU 개수 | `count by(Hostname)(DCGM_FI_DEV_GPU_UTIL)` |
| 실행 중인 컨테이너 수 | `sum by(cluster)(cluster_monitor_container_running)` |

지표 하나를 가져오지 못해도 나머지는 보여 줍니다. Prometheus가 내려가 있어도 API는 빈 값으로 200을 돌려줍니다.

## 6. Google Sheets (발급 내역)

운영 스택에서만 켭니다(`issuance-sheet.enabled`). 컨테이너가 살아 있는 신청을 서버별 탭에 옮겨 적습니다.

- 주기적으로 돌지 않습니다. **신청이나 포트가 바뀐 직후**와 서버가 뜬 직후에만 옮깁니다.
- 탭을 **통째로 다시 씁니다.** 사람이 탭을 손으로 고쳐도 다음 변경 때 덮어씁니다.
- 실패하면 잠시 뒤 다시 시도합니다. 요청을 처리하는 흐름과 별도 스레드라 Google이 느려도 승인이 느려지지 않습니다.
- 설정 값이 있다는 것만으로는 켜지지 않습니다. 운영 설정을 복사해 쓰는 실험 스택이 운영 문서를 고치지 않게 하기 위해서입니다.

!!! note "서버마다 다른 값은 설정에"
    접속 주소, 포트 대역, 알림 채널처럼 환경마다 다른 값은 코드에 적지 않고 설정(`app.servers.*`)에 둡니다. 서버가 늘어나면 설정 항목만 추가합니다.
