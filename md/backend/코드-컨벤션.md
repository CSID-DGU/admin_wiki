# 코드 컨벤션

이 저장소가 실제로 지키는 규칙입니다. 규칙마다 이유를 함께 적었습니다. 규칙만 외우면 처음 보는 상황에서 판단이 서지 않기 때문입니다. 코드에서 "왜 이렇게 돼 있지?" 싶으면 여기서 먼저 찾습니다.

## 한눈에 보기

| 주제 | 규칙 |
| --- | --- |
| 패키지 | 업무 영역별로 나누고, 그 안을 계층별로 나눈다 |
| 이름 | 관리자 전용은 `Admin`으로 시작, 조회와 변경 서비스는 분리 |
| 엔티티 | Setter 없음. 상태는 의도가 드러나는 메서드로만 바꾼다 |
| DTO | `record`로 만든 불변 객체. 입력 검증은 DTO에 |
| 트랜잭션 | 외부 호출과 알림을 트랜잭션 안에 넣지 않는다 |
| 오류 | 서비스에서 `BusinessException(ErrorCode)`를 던진다 |
| 스키마 | Flyway 파일로만 바꾼다 |
| 테스트 | 병합 전 CI 통과 필수 |

## 1. 패키지 구조

```
domain/
└── {업무 영역}/
    ├── controller/
    │   └── docs/        API 문서용 인터페이스
    ├── service/
    ├── entity/
    ├── repository/
    └── dto/
        ├── request/
        └── response/
```

공통 기능은 `global/` 아래에, 오류 코드와 오류 응답은 `error/`에 둡니다. 영역 목록은 [시스템 아키텍처](시스템-아키텍처.md) 6절에 있습니다.

기술(컨트롤러끼리, 서비스끼리)이 아니라 업무 영역으로 먼저 나누는 이유는, 기능 하나를 고칠 때 봐야 할 파일이 한 폴더에 모이기 때문입니다.

## 2. 이름 짓기

### 클래스

| 유형 | 규칙 | 예 |
| --- | --- | --- |
| 컨트롤러 (사용자) | `{대상}Controller` | `RequestController`, `UserController` |
| 컨트롤러 (관리자) | `Admin`으로 시작 | `AdminRequestController`, `AdminUserController` |
| 서비스 (조회) | `{대상}QueryService` | `RequestQueryService` |
| 서비스 (변경) | `{대상}CommandService` | `RequestCommandService` |
| 서비스 (한 가지 역할) | 역할을 이름에 | `RequestExpiryService`, `PodMigrationService` |
| 예약 작업 | 정해진 시각이면 `…Scheduler`, 결과 확인이면 `…JobPoller` | `HomeCleanupScheduler`, `ProvisionJobPoller` |
| 요청 DTO | `{동작}RequestDTO` 또는 `{동작}DTO` | `SaveRequestRequestDTO`, `ApproveRequestDTO` |
| 응답 DTO | `{내용}ResponseDTO` | `UserResponseDTO` |

관리자용을 이름으로 구분하는 이유는 파일 이름만 보고 권한 범위를 알 수 있게 하기 위해서입니다. `/api/admin/**` 경로는 관리자 권한이 있어야 열립니다.

### 메서드

| 동작 | 접두사 | 예 |
| --- | --- | --- |
| 조회 | `get…` | `getMyInfo` |
| 생성 | `create…` | `createRequest` |
| 수정 | `update…` | `updatePhone` |
| 업무 동작 | 업무 용어 그대로 | `approveRequest`, `rejectRequest` |
| 상태 이동 (엔티티) | 시작은 `begin…`, 끝은 `end…`/`complete…` | `beginExpiry`, `completeApproval` |

## 3. 엔티티

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
@Table(name = "users")
public class User extends BaseTimeEntity { ... }
```

| 규칙 | 이유 |
| --- | --- |
| Setter와 `@Data`를 쓰지 않는다 | 어디서든 값을 바꿀 수 있으면 상태가 언제 왜 바뀌었는지 추적할 수 없다 |
| 상태는 메서드로 바꾼다 (`request.beginExpiry()`) | 바꿔도 되는 조건을 엔티티가 한 곳에서 확인한다 |
| 기본 생성자는 `PROTECTED` | JPA는 쓸 수 있고, 바깥 코드는 빈 객체를 만들지 못한다 |
| enum은 `@Enumerated(EnumType.STRING)` | 순서 번호로 저장하면 enum 순서가 바뀔 때 기존 데이터의 뜻이 바뀐다 |
| 연관 관계는 `FetchType.LAZY` | 필요 없는 조회를 막는다 |
| `BaseTimeEntity`를 상속 | 생성·수정 시각을 한 곳에서 자동 기록한다 |

`Request`의 상태 이동은 `Status`에 적힌 허용 표를 따릅니다. 표에 없는 이동을 시도하면 예외가 납니다.

## 4. DTO

```java
public record SaveRequestRequestDTO(
        @NotNull Integer resourceGroupId,
        @NotNull Long imageId,
        @Future LocalDateTime expiresAt,
        ...
) { }
```

- Java `record`로 만들어 값이 바뀌지 않게 합니다.
- 입력 검증은 DTO의 어노테이션으로 하고, 컨트롤러에서 `@Valid`로 실행합니다.
- 여러 곳에서 쓰는 규칙은 전용 어노테이션으로 만듭니다(`@UbuntuUsername`, `@PhoneNumber`, `@MaxUtf8Bytes`).
- 응답 DTO는 엔티티를 받아 변환하는 정적 메서드(`fromEntity`)를 둡니다.

!!! note "글자 수와 바이트 수는 다르다"
    `@Size`는 글자 수를 셉니다. 비밀번호처럼 바이트로 한도가 정해진 값(BCrypt는 72바이트)은 한글이 섞이면 `@Size`를 통과하고도 서버 오류로 끝납니다. 이런 값에는 `@MaxUtf8Bytes`를 함께 답니다.

## 5. 계층별 역할

| 계층 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 컨트롤러 | 요청 받기, 입력 검증 실행, 로그인한 사용자 꺼내기, 서비스 호출, 응답 | 업무 판단 |
| 서비스 | 업무 규칙, 트랜잭션, 외부 호출 순서 | HTTP 세부 사항 |
| 리포지토리 | DB 조회·저장 | 업무 판단 |
| 엔티티 | 자기 상태를 바꿔도 되는지 확인하고 바꾸기 | 다른 서비스 호출 |

API 문서용 어노테이션은 컨트롤러에 직접 달지 않고 `controller/docs/`의 인터페이스에 답니다. 컨트롤러가 그 인터페이스를 구현합니다. 문서용 어노테이션이 길어 실제 코드가 묻히는 것을 막기 위해서입니다.

## 6. 조회와 변경을 나눈다

한 서비스가 읽기와 쓰기를 모두 맡으면 트랜잭션 설정이 섞이고 책임이 흐려집니다.

```java
@Service
@Transactional(readOnly = true)
public class RequestQueryService { ... }   // 조회만

@Service
@Transactional
public class RequestCommandService { ... } // 변경만
```

트랜잭션은 **클래스에 한 번** 선언합니다. 메서드마다 따로 달면 빠뜨린 메서드가 생깁니다.

## 7. 트랜잭션 안에서 하지 않는 일

트랜잭션 안에서는 **DB 작업만** 합니다. config-server 호출, 메일·Slack 전송은 트랜잭션 밖에서 합니다.

| 트랜잭션 안에서 하면 | 생기는 문제 |
| --- | --- |
| 외부 호출 | 응답이 느린 동안 DB 연결과 행 잠금을 쥐고 있다. 다른 요청이 줄줄이 멈춘다 |
| 알림 전송 | 저장이 취소돼도 알림은 이미 나갔다 |

그래서 다음처럼 씁니다.

- 외부 호출이 끼는 서비스는 클래스 전체에 트랜잭션을 걸지 않고, 상태를 바꾸는 구간만 `TransactionTemplate`으로 짧게 묶습니다(`AdminRequestCommandService`).
- 알림은 `AfterCommit.run(...)`으로 감싸 저장이 확정된 뒤에 보냅니다.

구체적인 방법은 [핵심 설계 패턴](핵심-설계-패턴.md) 1·2번에 있습니다.

## 8. 오류 처리

```java
User user = userRepository.findById(userId)
        .orElseThrow(() -> new BusinessException(ErrorCode.USER_NOT_FOUND));
```

1. 서비스에서 조건이 맞지 않으면 `BusinessException`에 `ErrorCode`를 담아 던집니다.
2. `GlobalExceptionHandler`가 받아 `ErrorCode`에 적힌 HTTP 상태와 메시지로 응답합니다.

| 규칙 | 이유 |
| --- | --- |
| 메시지와 상태 코드는 `ErrorCode`에만 적는다 | 같은 오류가 곳곳에서 다른 문구로 나가지 않게 |
| 메시지는 화면에 그대로 보인다고 생각하고 쓴다 | 실제로 그대로 보인다. 무엇을 하면 되는지까지 적는다 |
| 상태 코드는 화면의 반응을 생각해 고른다 | 401은 화면이 "로그인 만료"로 처리해 다시 로그인시킨다. 로그인이 풀려야 하는 상황에만 401을 쓴다 |
| 새 오류를 만들기 전에 비슷한 것이 있는지 본다 | [에러 코드 카탈로그](에러-코드-카탈로그.md) |

## 9. 응답 형식

```json
// 성공
{ "status": 200, "message": "요청이 성공했습니다.", "data": { ... } }

// 실패
{ "status": 404, "message": "사용자를 찾을 수 없습니다.", "code": "USER_NOT_FOUND" }
```

| 상황 | 쓰는 메서드 | 상태 |
| --- | --- | --- |
| 조회·처리 성공 | `SuccessResponse.ok(data)` | 200 |
| 새로 만듦 | `SuccessResponse.created(data)` | 201 |
| 작업만 등록함 (결과는 나중) | `SuccessResponse.accepted(data)` | 202 |

실패 응답의 `code`는 `ErrorCode`의 이름입니다. 화면은 메시지 문구가 아니라 이 값으로 분기합니다. 문구는 바뀔 수 있지만 이름은 바꾸지 않습니다.

## 10. 로그

| 레벨 | 쓰는 때 |
| --- | --- |
| `INFO` | 주요 업무 사건 (신청, 승인, 회수) |
| `WARN` | 규칙 위반, 일시적 실패, 스스로 회복할 수 있는 문제 |
| `ERROR` | 사람이 봐야 하는 실패 |
| `DEBUG` | 개발 중 확인용 |

```java
log.info("[createRequest] 요청 생성: userId={}, resourceGroupId={}", userId, dto.resourceGroupId());
```

!!! warning "로그에 남기지 않는 것"
    비밀번호, 토큰, 인증번호는 남기지 않습니다. 이메일은 가려서 남깁니다(`EmailAddresses.mask`). 저장소가 공개돼 있으므로 CI 로그에도 서버 주소·계정 이름·설정값이 찍히지 않게 합니다.

## 11. 조회 성능

목록을 조회한 뒤 건마다 연관 데이터를 따로 읽으면 조회가 건수만큼 늘어납니다(N+1). 함께 쓸 연관 데이터는 한 번에 가져옵니다.

```java
@Query("SELECT r FROM Request r " +
       "JOIN FETCH r.user " +
       "LEFT JOIN FETCH r.resourceGroup " +
       "LEFT JOIN FETCH r.containerImage " +
       "WHERE r.status IN :statuses AND r.createdAt >= :createdFrom " +
       "ORDER BY r.requestId DESC")
List<Request> findAllForAdminList(...);
```

한 건에 하나씩인 연관(사용자, GPU 종류, 이미지)만 함께 가져옵니다. 그룹처럼 여러 건인 연관을 둘 이상 함께 조인하면 결과 행이 곱으로 불어나므로, 그런 것은 번호로 묶어 따로 한 번 읽습니다.

같은 행을 두 요청이 동시에 바꿀 수 있는 곳에서는 행을 잠그고 읽습니다(`findByIdForUpdate`). 잠근 뒤에는 **상태를 다시 확인**합니다. 기다리는 사이에 다른 요청이 먼저 바꿨을 수 있기 때문입니다.

## 12. 테스트

```bash
./gradlew test
```

테스트는 메모리 DB(H2)와 가짜 설정값만 써서 외부 서비스 없이 돕니다. PR을 올리면 CI가 전체 테스트를 돌리고, 통과해야 병합할 수 있습니다.

| 종류 | 도구 | 확인하는 것 |
| --- | --- | --- |
| 서비스 단위 테스트 | Mockito | 업무 규칙. 외부 의존은 가짜로 바꾼다 |
| 컨트롤러 테스트 | `@WebMvcTest` + MockMvc | 요청·응답 형식, 입력 검증, 오류가 어떤 상태 코드로 나가는지 |
| 리포지토리 테스트 | `@DataJpaTest` + H2 | 직접 쓴 쿼리가 맞는지 |
| 통합 테스트 | `@SpringBootTest` | 보안 설정처럼 전체가 떠야 확인되는 것 |

- 테스트 이름은 `@DisplayName`에 **한국어 문장**으로 씁니다. "어떤 상황에서 어떤 결과가 나온다"가 드러나야 합니다.
- 관련된 테스트는 `@Nested`로 묶습니다.
- 컨트롤러 테스트는 `WebMvcTestSupport`를 상속합니다. 보안 설정에 필요한 공통 가짜 객체가 들어 있습니다.
- 성공하는 경우뿐 아니라 **실패하는 경우와 경계 값**을 함께 씁니다. 이 시스템의 버그는 대부분 "작업이 실패했을 때", "두 요청이 겹쳤을 때"에서 나왔습니다.

```java
@Nested
@DisplayName("login (로그인)")
class Login {
    @Test
    @DisplayName("비밀번호가 틀리면 UnauthorizedException을 던진다")
    void login_throwsException_whenPasswordWrong() { ... }
}
```

코드와 어긋나면 실패하도록 만들어 둔 테스트가 몇 개 있습니다. 실패하면 테스트를 고치지 말고 가리키는 곳을 함께 고칩니다.

| 테스트 | 지키는 것 |
| --- | --- |
| `LifecycleTransitionTableTest` | `Status`의 허용 표와 `lifecycle-transitions.yaml`이 같은가 |
| `RuntimeDefaultsTest` | 예약 작업 수와 스레드 수가 맞는가 |

## 13. 브랜치와 PR

네 저장소가 같은 규칙을 씁니다. 전문은 [브랜치·배포 규칙](../브랜치-규칙.md)입니다.

- `main`에 직접 올리지 않습니다. 작업 브랜치를 만들어 PR로 병합합니다.
- 병합은 squash, 커밋 메시지는 `fix: …`, `feat: …` 형식입니다.
- 설정 파일(`application.yml`)을 바꿨다면 PR 본문에 적습니다. 저장소에 없는 파일이라 적지 않으면 아무도 모릅니다.
- 스키마를 바꿨다면 Flyway 파일이 함께 있어야 합니다.
