# 핵심 설계 패턴

이 코드에는 여러 곳에서 되풀이해 만나는 문제가 있고, 그때마다 쓰는 해법이 정해져 있습니다. 새 기능을 만들다가 비슷한 문제를 만나면 새로 고민하기 전에 여기에 답이 있는지부터 봅니다.

## 한눈에 보기

| # | 만나는 문제 | 정해진 해법 |
| --- | --- | --- |
| 1 | 저장이 취소됐는데 알림은 이미 나갔다 | 알림은 저장이 확정된 뒤에 보낸다 |
| 2 | 외부 호출이 느려 DB가 묶인다 | 트랜잭션을 짧게, 외부 호출은 밖에서 |
| 3 | 몇 분 걸리는 일을 요청 하나가 기다린다 | 작업 등록 후 결과는 따로 확인한다 |
| 4 | 실패했는지 성공했는지 모른다 | 모르면 되돌리지 않고 사람에게 넘긴다 |
| 5 | 같은 대상을 두 요청이 동시에 바꾼다 | 진행형 상태로 선점하고, 행을 잠근 뒤 다시 확인한다 |
| 6 | 화면에는 됐다고 나오는데 실제는 아니다 | DB는 인프라가 바뀐 것을 확인한 뒤에 바꾼다 |
| 7 | 같은 알림이 반복해서 나간다 | Redis에 "보냄" 표시를 남긴다 |
| 8 | 누군가 같은 요청을 끝없이 보낸다 | Redis로 횟수를 센다 |
| 9 | Slack이 느려 승인이 느려진다 | 대기열에 넣고 따로 보낸다 |
| 10 | 가입 여부가 응답으로 새어 나간다 | 가입 여부와 상관없이 똑같이 응답한다 |

## 1. 알림은 저장이 확정된 뒤에

### 문제

서비스가 DB를 바꾸는 도중에 메일을 보내면, 그 뒤에 오류가 나 저장이 취소돼도 메일은 이미 나갔습니다. 사용자는 "승인됐다"는 메일을 받았는데 DB에는 그런 기록이 없습니다.

### 해법

알림을 `AfterCommit.run(...)`으로 감쌉니다. 저장이 확정(커밋)된 뒤에만 실행되고, 취소되면 실행되지 않습니다.

```java
String name = user.getName();          // 값은 지금(트랜잭션 안에서) 읽어 두고
String email = user.getEmail();
AfterCommit.run("만료 예고, 요청 ID " + requestId,
        () -> alarmService.notifyUser(name, email, subject, body));  // 전송만 뒤로 미룬다
```

- 알림에 쓸 값은 **미리 읽어** 변수에 담아 둡니다. 저장이 끝난 뒤에는 엔티티의 연관 데이터를 읽지 못할 수 있습니다.
- 미룬 일이 실패해도 예외를 밖으로 내지 않고 기록만 합니다. 이미 확정된 처리를 실패로 보이게 하지 않기 위해서입니다.
- 저장이 취소돼도 해야 하는 일(예: 거절하면서 그 사실을 알림)은 `AfterTransaction`을 씁니다.

같은 목적으로 Spring의 `@TransactionalEventListener(phase = AFTER_COMMIT)`도 씁니다. 회수 완료 안내(`RequestExpiredEvent`), 발급 내역 시트 갱신(`RequestRowChangedEvent`)이 이 방식입니다.

## 2. 트랜잭션은 짧게

### 문제

트랜잭션 안에서 config-server를 부르면, 응답이 올 때까지 DB 연결과 행 잠금을 쥐고 있습니다. config-server가 느려지면 Admin BE의 다른 요청까지 줄줄이 멈춥니다.

### 해법

상태를 바꾸는 구간만 짧은 트랜잭션으로 묶고, 외부 호출은 그 사이에 둡니다.

```
① 짧은 트랜잭션: 행을 잠그고 상태를 확인한 뒤 진행형으로 바꿔 저장
② 트랜잭션 밖:   config-server에 작업 등록
③ 짧은 트랜잭션: 받은 작업 번호를 기록
```

이런 서비스는 클래스 전체에 트랜잭션을 걸지 않고 `TransactionTemplate`으로 필요한 구간만 묶습니다. `AdminRequestCommandService`, `RequestExpiryService`가 예입니다.

### 같은 클래스 안에서 부르면 트랜잭션이 걸리지 않는다

`@Transactional`은 바깥에서 그 객체를 부를 때만 동작합니다. 같은 클래스의 다른 메서드를 `this.method()`로 부르면 걸리지 않습니다.

```java
// 잘못된 예 — processOne의 @Transactional이 적용되지 않는다
public void runAll() {
    for (Long id : ids) this.processOne(id);
}
```

그래서 "여러 건을 돌면서 건마다 따로 저장"해야 하는 곳은 건별 처리를 **다른 클래스**로 떼어 냅니다. `UserSchedulerService`(반복)와 `UserLifecycleTransactionalService`(건별 트랜잭션)가 그 예입니다. 이렇게 하면 한 건이 실패해도 나머지 건은 영향받지 않습니다.

## 3. 작업 등록 후 결과는 따로 확인

### 문제

컨테이너 생성은 길게는 몇 분 걸립니다. 승인 요청이 그동안 기다리면 화면 연결이 끊기고, 그 사이 Admin BE가 재시작되면 어디까지 됐는지 알 수 없습니다.

### 해법

```
요청을 받으면  →  상태를 진행형으로 바꾸고 작업을 등록한 뒤 바로 202 응답
폴러가 3초마다 →  결과를 조회해 끝났으면 DB에 반영
```

생성·이동·회수·비밀번호·그룹·포트·접속 차단·홈 삭제가 모두 이 방식입니다. 새로 인프라 작업이 필요한 기능을 만들 때도 config-server에 "기다렸다가 답하는" 경로를 만들지 말고 **작업 종류를 추가**합니다.

폴러를 새로 만들 때는 `JobResultPoller`의 규칙을 따릅니다.

| 규칙 | 이유 |
| --- | --- |
| 작업 번호가 다른 결과는 반영하지 않는다 | 같은 신청의 이전 작업 결과일 수 있다 |
| 한 건의 실패가 나머지 건을 막지 않는다 | 건마다 예외를 잡는다 |
| 결과 조회 자체가 실패하면 기록만 하고 다음 바퀴에 다시 | 네트워크가 잠깐 끊기는 일은 흔하다 |
| 예약 작업 스레드 수를 함께 올린다 | [시스템 아키텍처](시스템-아키텍처.md) 4절 |

## 4. 모르면 되돌리지 않는다

### 문제

작업이 "실패"로 끝났는데 컨테이너는 만들어져 있을 수 있습니다. 응답을 받지 못해 등록됐는지조차 모를 수도 있습니다. 이때 신청을 `PENDING`으로 되돌리면, 관리자가 다시 승인했을 때 **컨테이너가 하나 더** 만들어집니다.

### 해법

결과를 네 가지로 나누어 다르게 처리합니다.

| 상황 | 처리 |
| --- | --- |
| 실패했고 남은 자원이 없다 | 직전 상태로 되돌린다. 다시 시도할 수 있다 |
| 실패했는데 자원이 남았다 (`DEGRADED`) | **그대로 둔다.** 관리자에게 알린다 |
| 결과를 알 수 없다 (`UNKNOWN`) | **그대로 둔다.** 관리자에게 알린다 |
| 등록 요청에 답을 받지 못했다 | 등록되지 않았다고 단정하지 않는다. 결과를 조회해 작업이 있는지 먼저 본다 |

"그대로 둔다"는 신청이 진행형 상태에 남는다는 뜻입니다. 관리자가 실제 상태를 확인한 뒤 정리합니다. 자동으로 되돌려 편해지는 것보다, 잘못 되돌려 자원이 중복되거나 주인을 잃는 쪽이 훨씬 비쌉니다.

예외도 있습니다. 비밀번호·그룹·포트·접속 차단 작업은 **몇 번을 다시 해도 결과가 같은** 일입니다(이미 맞춰진 부분은 건드리지 않고 나머지만 맞춤). 그래서 이들은 결과가 불명이어도 실패로 닫고 다시 요청하게 합니다. 새 작업이 어느 쪽인지는 "다시 실행해도 안전한가"로 판단합니다.

재조정(5분마다)도 같은 원칙입니다. 진행형 상태에 오래 멈춘 신청을 시간만 보고 되돌리지 않고, **작업 상태를 조회해** 작업이 없거나 실패로 끝났을 때만 되돌립니다.

## 5. 동시에 들어온 요청

### 문제

관리자 두 명이 같은 신청을 동시에 승인하거나, 승인과 거절이 겹치거나, 회수가 도는 중에 이동을 누를 수 있습니다.

### 해법

세 가지를 함께 씁니다.

**① 진행형 상태로 선점한다.** 일을 시작하기 전에 상태를 `PROCESSING`·`MIGRATING`·`EXPIRING`으로 바꿔 **먼저 저장**합니다. 다른 요청은 상태를 보고 "이미 처리 중"으로 거절됩니다.

**② 행을 잠근 뒤 상태를 다시 확인한다.**

```java
Request req = requestRepository.findByIdForUpdate(requestId)   // 이 행을 잠근다
        .orElseThrow(...);
if (req.getStatus() != Status.PROCESSING) {                    // 기다리는 사이 바뀌었을 수 있다
    return;
}
```

잠금을 얻기까지 기다리는 사이 다른 요청이 먼저 바꿨을 수 있습니다. 잠근 뒤에 본 값만 믿습니다.

**③ 잠그는 순서를 통일한다.** 여러 행을 잠글 때는 **신청 → 사용자 → 그룹** 순서로 잠급니다. 순서가 엇갈리면 두 요청이 서로를 기다리며 멈춥니다(교착).

## 6. DB는 인프라가 바뀐 뒤에

### 문제

그룹 추가를 승인하면서 DB부터 바꾸면, 화면에는 "그룹에 속함"으로 나오는데 실제 컨테이너에서는 권한이 없습니다. 작업이 실패하면 이 어긋남이 그대로 남습니다.

### 해법

**작업이 성공한 것을 확인한 뒤에** DB를 바꿉니다.

| 대상 | 바꾸는 시점 |
| --- | --- |
| 계정이 속한 그룹 (`user_groups`) | 그룹 작업 성공 후 |
| 열린 포트 (`pod_external_ports`, `port_requests`) | 포트 작업 성공 후 |
| 비밀번호 해시 두 개 | 비밀번호 작업 성공 후 |
| 계정 번호(UID/GID), Pod 이름 | 생성 작업 성공 후 |

그 전까지는 "반영 중" 상태로 두어, 화면이 아직 끝나지 않았음을 보여 줍니다.

## 7. 같은 알림을 반복하지 않는다

### 문제

예약 작업은 주기적으로 같은 대상을 다시 봅니다. 그대로 두면 만료 예고가 하루에 두 번 나가거나, 결과 불명인 신청의 알림이 3초마다 나갑니다.

### 해법

Redis에 "이 사건은 알렸다"는 키를 **없을 때만** 만들고(`SETNX`), 이미 있으면 건너뜁니다. 키에는 TTL을 주어 저절로 사라지게 합니다.

| 용도 | 방법 | 유지 시간 |
| --- | --- | --- |
| 만료 예고, 장기 미사용 경고 | 대상·남은 날·날짜로 키를 만든다 | 25시간 |
| 관리자 알림 (결과 불명 등) | `AlertDeduplicator`에 사건 키를 넘긴다 | 7일 |

```java
if (!alertDeduplicator.firstOccurrence("provision-missing-result:" + requestId + ":" + jobId)) {
    return;   // 이미 알린 사건
}
```

키에 **작업 번호**를 넣는 것이 요령입니다. 같은 신청이라도 새 작업이면 새 사건으로 다시 알리게 됩니다.

**Redis에 닿지 못하면 알림을 보냅니다.** 못 받는 것보다 두 번 받는 편이 낫다고 판단했습니다. 메모리가 아니라 Redis에 두는 이유는, Admin BE가 재시작돼도 같은 알림이 다시 나가지 않게 하기 위해서입니다.

## 8. 횟수 제한

### 문제

로그인한 사용자라면 누구나 부를 수 있는 기능을 반복 호출하면, 관리자 검토 대기열이나 알림 채널, 노드 디스크가 찹니다. 로그인하지 않아도 부를 수 있는 인증 메일은 남의 주소로 메일을 쏟아붓는 데 쓰일 수 있습니다.

### 해법

`RedisWindowCounter`로 "처음 한 때부터 일정 시간 동안 몇 번"을 셉니다.

| 대상 | 한도 |
| --- | --- |
| 로그인 실패 | 이메일당 15분에 5번 |
| 인증 메일 발송 | 주소당 1분에 1번, 1시간에 5번 |
| 인증번호 입력 | 번호 하나당 5번 틀리면 폐기 |
| 컨테이너 신청 | 사용자당 하루 5건 |
| 그룹 만들기 | 사용자당 하루 5개 |
| 본인 컨테이너 재시작 | 사용자당 1시간에 5번 |

횟수를 올리는 것과 만료 시간을 거는 것을 **한 번에** 합니다. 따로 하면 그 사이에 서버가 죽었을 때 만료 없는 키가 남아, 그 사용자가 영원히 막힙니다. 직접 `INCR`·`EXPIRE`를 쓰지 말고 `RedisWindowCounter`를 씁니다.

## 9. Slack은 대기열로

### 문제

Slack 응답을 기다리면 승인·회수가 그만큼 느려집니다. Slack에는 초당 전송 제한도 있습니다.

### 해법

```
알림 발생 → Redis 목록 끝에 넣고 바로 돌아옴
전송 작업 → 1초마다 앞에서 하나 꺼내 Slack으로 전송
```

| 실패 종류 | 처리 |
| --- | --- |
| 일시적 장애 (네트워크, Slack 장애) | 다시 넣어 최대 3번 재시도 |
| 다시 해도 같은 실패 (받는 사람이 Slack에 없음) | 버린다 |
| 설정이 죽음 (웹훅 삭제, 토큰 폐기) | `ERROR` 로그로 남긴다. 사람이 고쳐야 한다 |

Admin BE의 알림과 config-server가 보내는 인프라 알림은 대기열과 전송 작업을 따로 씁니다. 한쪽이 밀려도 다른 쪽이 늦어지지 않습니다. Redis 자체가 죽어 대기열에 넣지 못하면 그 자리에서 직접 보냅니다.

## 10. 가입 여부를 드러내지 않는다

### 문제

"이미 가입된 이메일입니다"라고 답하면, 로그인하지 않은 누구나 어떤 주소가 가입돼 있는지 알아낼 수 있습니다. 응답 문구가 같아도 **응답 시간**이 다르면 마찬가지입니다.

### 해법

| 기능 | 처리 |
| --- | --- |
| 인증 메일 요청 | 가입 여부와 상관없이 같은 응답. 이미 가입된 주소에는 인증번호 대신 안내 메일을 보낸다 |
| 비밀번호 재설정 번호 요청 | 누구에게나 200. 메일은 응답과 따로 보내 응답 시간이 같게 한다 |
| 로그인 | 없는 이메일에도 비밀번호 검사를 한 번 돌려 응답 시간을 맞춘다. 비활성 계정이라는 안내는 비밀번호가 맞은 뒤에만 한다 |
| 계정 이름 중복 확인 | 로그인한 사용자만 쓸 수 있다 |

로그인 없이 부를 수 있는 기능을 새로 만들 때는 "이 응답으로 무엇을 알아낼 수 있는가"를 먼저 따집니다.
