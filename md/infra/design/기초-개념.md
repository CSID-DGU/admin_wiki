## 1. 리눅스 계정과 파일 권한

### 1.1 UID와 GID

리눅스는 사용자와 그룹을 이름뿐 아니라 숫자로도 구분한다. 사용자 번호는 UID, 그룹 번호는 GID이다.

파일에도 사용자 이름이 아닌 UID와 GID가 소유권 정보로 기록된다. 예를 들어 파일의 소유자가 `dongmin`으로 보이더라도, 실제 디스크에는 `UID 2041`과 같은 숫자가 저장된다.

이름과 숫자의 대응 관계는 다음 파일에서 관리한다.

| 파일       | 역할                     |
| -------- | ---------------------- |
| `passwd` | 사용자 이름, UID, 기본 GID를 기록한다. |
| `group`  | 그룹 이름, GID, 그룹 구성원을 기록한다. |

### UID를 정하는 곳

NFS에 저장된 사용자 홈 디렉터리 역시 UID 숫자를 기준으로 소유권을 판단한다. 따라서 동일한 NAS를 사용하는 FARM 서버와 Kubernetes Pod는 반드시 동일한 UID 대응 관계를 사용해야 한다.

서버마다 같은 UID를 다른 사용자에게 배정하면, 특정 사용자가 다른 사용자의 홈 디렉터리를 자신의 파일처럼 읽거나 수정할 수 있다.

이를 막기 위해 config-server가 `/kube_share/passwd`를 계정 정보의 기준 파일로 사용하고 UID도 여기서 정한다. AD에도 같은 번호(RFC2307 uidNumber)로 계정을 만든다. 홈은 Kerberos(`sec=krb5`)로 마운트되어 NAS가 AD를 보고 사용자를 판정하기 때문이다.

한 번 준 UID는 계정이 지워져도 다른 사람에게 다시 주지 않는다. 회수 때 홈을 보존하므로, 번호를 재사용하면 새 사용자가 옛 사용자의 홈을 넘겨받는다. 그래서 지금까지 발급한 최댓값을 `/kube_share/issued_id_max.json`에 따로 기록한다.

### 1.2 passwd, group, shadow, sudoers

| 파일        | 저장 내용                        | 주의사항                               |
| --------- | ---------------------------- | ---------------------------------- |
| `passwd`  | 사용자 이름, UID/GID, 홈 경로, 로그인 셸 | 암호 정보는 없으며 누구나 읽을 수 있다.            |
| `group`   | 그룹 이름, GID, 그룹 멤버            | 그룹 권한 관리에 사용한다.                    |
| `shadow`  | 사용자 암호 해시                    | root만 읽을 수 있다.                     |
| `sudoers` | sudo 사용 권한                   | 문법 오류가 발생하면 sudo 전체가 동작하지 않을 수 있다. |

일반적인 리눅스 환경에서는 `/etc/passwd`, `/etc/group` 등을 `useradd`와 같은 명령으로 관리한다.

### 계정 파일을 쓰는 방법

여기서는 config-server가 NFS의 `/kube_share`에 저장된 계정 파일을 직접 수정해 UID/GID 배정 기록으로 사용한다.

사용자 Pod에는 이 파일들을 직접 마운트하지 않는다. 대신 다음 순서로 사용자를 생성한다.

1. config-server가 `/kube_share/passwd`에서 UID/GID를 조회한다.
2. 조회한 값을 Pod 환경변수로 주입한다.
3. 컨테이너 entrypoint가 전달받은 UID/GID로 내부 사용자를 생성한다.

계정 파일을 컨테이너의 `/etc`에 직접 마운트하던 방식은 더 이상 쓰지 않는다.

### 1.3 chmod 711

`chmod`의 세 숫자는 차례대로 다음 권한을 의미한다.

1. 파일 소유자
2. 소유 그룹
3. 기타 사용자

각 권한 값은 다음 숫자의 합으로 표현한다.

| 권한            |  값 |
| ------------- | -: |
| 읽기            |  4 |
| 쓰기            |  2 |
| 실행 또는 디렉터리 진입 |  1 |

따라서 `chmod 711`은 다음과 같은 권한 설정이다.

| 대상     | 권한         |
| ------ | ---------- |
| 소유자    | 읽기, 쓰기, 진입 |
| 그룹     | 진입만        |
| 기타 사용자 | 진입만        |

디렉터리의 "진입"(x)은 그 안으로 지나갈 수 있다는 뜻이고, "읽기"(r)는 안의 이름 목록을 볼 수 있다는 뜻이다. 진입만 있으면 목록은 볼 수 없지만, 안쪽 폴더의 이름을 알고 그 폴더에 권한이 있으면 들어갈 수 있다.

### 홈 디렉터리 권한

모든 사용자 홈 디렉터리는 `chmod 711`로 생성한다. 사용자별 PVC는 만들지 않고, 홈 사이의 접근은 UID 소유권과 권한으로 나눈다.

| 장치 | 효과 |
| --- | --- |
| 홈 `711` | 다른 사용자는 홈 목록을 볼 수 없고 지나가기만 한다 |
| 컨테이너 `umask 007` | 새 파일·폴더는 기타 사용자 권한 없이 만들어진다. 이름을 알아도 열리지 않는다 |
| 팀 공유 | 사용자가 홈 아래 폴더를 팀 그룹으로 바꾸면(`chgrp <팀> 폴더` + `chmod 2770 폴더`) 팀원이 그룹 권한으로 들어온다 |

예전에는 홈을 `700`으로 막고 팀 공유용으로 홈 밖에 팀 디렉터리(`/home/_g_<팀>`)를 따로 만들었다. 지금은 팀 디렉터리를 만들지 않는다.

## 2. NFS와 NAS

### 2.1 NFS와 NAS

NFS(Network File System)는 다른 서버의 디렉터리를 내 서버의 디렉터리처럼 쓰게 하는 방식이다.

서버가 특정 디렉터리를 외부에 공개하면(export), 클라이언트는 해당 경로를 자신의 파일시스템에 마운트한다. 이후 `ls`, `cat`, 파일 저장 등의 작업은 로컬 파일처럼 보이지만 실제로는 네트워크 통신을 통해 처리된다.

NAS(Network Attached Storage)는 이 NFS 저장소를 제공하는 장비다.

### NAS에 저장하는 데이터

이 시스템의 NAS에는 다음 데이터가 저장된다.

* 사용자 홈 디렉터리
* `/kube_share` 계정 파일(스택마다 하위 폴더)

따라서 NAS에 문제가 생기면 사용자 파일과 계정 관리가 함께 영향을 받는다. 이 저장소를 대신할 장비가 구성되어 있지 않으므로 NAS 장애는 전체 서비스에 영향을 준다. 스택 DB는 NAS가 아니라 노드 로컬 디스크에 있고, 매일 다른 노드로 백업한다([데이터베이스](데이터베이스.md)).

---

### 2.2 root_squash

`root_squash`는 NFS의 기본 보안 기능이다.

NFS 클라이언트의 root 사용자가 공유 디렉터리에 접근하면, NFS 서버는 그 요청을 `nobody` 같은 익명 사용자 권한으로 처리한다.

그래서 한 클라이언트 서버에서 root 권한을 얻더라도 NAS 파일 전체를 마음대로 바꾸기 어렵다.

### 홈 디렉터리를 만드는 방법

Pod 안의 프로세스가 root로 실행되더라도 NFS 위에서는 root 권한을 사용할 수 없다. 따라서 Pod가 NFS에 사용자 홈 디렉터리를 직접 생성하거나 소유권을 변경할 수 없다.

config-server는 Pod를 생성하기 전에 NAS에 SSH로 접속하여 다음 작업을 수행한다.

```bash
mkdir -p <사용자 홈>
chown <UID>:<GID> <사용자 홈>
chmod 711 <사용자 홈>
```

이미 있는 홈의 소유자가 다른 UID면 덮어쓰지 않고 멈춘다. 이 과정이 실패하면 Pod 생성도 실패한다.

---

### 2.3 NFS 파일 락

파일 잠금은 여러 프로세스가 같은 파일을 동시에 바꾸지 못하게 하는 장치다.

NFS 위의 파일 잠금은 네트워크와 별도 잠금 서비스에 의존하므로, 이 시스템에서는 계정 파일에 직접 적용하지 않는다.

### 현재 잠금 방식

계정 파일을 읽고 쓰는 동안 스택 DB의 이름 잠금(`SELECT GET_LOCK(...)`)을 잡는다. API 서버와 제어기는 서로 다른 Pod라 Pod 안 `/tmp`의 잠금 파일은 서로 보이지 않는다. DB 잠금은 두 프로세스가 같은 DB를 보므로 서로를 막는다. 30초 안에 잡지 못하면 잠금 없이 진행하지 않고 실패한다.

`LockedFile`(Pod 안 `/tmp` 잠금)도 남아 있지만, 같은 프로세스 안의 워커끼리만 순서를 맞춘다.

### 파일을 바꿔 끼우는 방식

계정 파일은 제자리에서 덮어쓰지 않는다. 같은 폴더의 임시 파일에 다 쓰고 디스크에 내린 뒤 이름을 바꿔 끼운다. 쓰는 도중 프로세스가 죽거나 NFS가 끊겨도 원래 파일에는 옛 내용이나 새 내용 하나만 온전히 남는다.

## 3. Kubernetes

### 3.1 클러스터와 노드

Kubernetes는 여러 서버를 하나의 컨테이너 실행 환경으로 묶어 관리하는 오케스트레이션 시스템이다.

* **클러스터**는 여러 노드로 구성된 전체 실행 환경이다.
* **노드**는 Pod가 실제로 실행되는 개별 서버이다.

Kubernetes에는 필요한 Pod와 Service의 내용을 API로 등록한다. Kubernetes는 등록된 내용과 실제 상태가 다르면 다시 맞추려고 한다.

### Pod와 Service 생성

현재는 config-server가 Pod와 Service 정보를 Kubernetes API에 보내고, Kubernetes가 이를 실행한다.

---

### 3.2 Pod

Pod는 Kubernetes가 컨테이너를 실행하는 최소 단위이다.

Pod 스펙에는 다음과 같은 정보가 포함된다.

* 컨테이너 이미지
* 환경변수
* 볼륨 마운트
* GPU 개수
* 실행할 노드
* 포트 설정

### 사용자 Pod 규칙

여기서는 승인된 신청 하나마다 Pod 하나를 만든다. 한 사용자가 신청을 여러 개 가지면 Pod도 여러 개다.

config-server는 Kubernetes 클라이언트 라이브러리를 이용해 사용자 Pod 스펙을 생성한다.

보통은 Kubernetes가 실행 노드를 고르지만, 이 시스템은 config-server가 Prometheus GPU 지표로 먼저 노드를 고른 뒤 Pod에 그 노드를 지정한다.

---

### 3.3 Service와 NodePort

Pod의 IP는 Pod가 재생성될 때 변경될 수 있다. Service는 이러한 Pod에 고정된 네트워크 접근 지점을 제공한다.

NodePort 타입 Service는 모든 Kubernetes 노드의 특정 포트를 열고, 해당 포트로 들어온 요청을 대상 Pod로 전달한다.

기본 NodePort 범위는 다음과 같다.

```text
30000~32767
```

### 사용자 Pod에 여는 포트

사용자 Pod의 각 포트마다 별도의 NodePort Service를 생성한다.

* SSH는 컨테이너 포트 22를 사용한다.
* Jupyter는 컨테이너 포트 8888을 사용한다.
* 사용자가 추가로 신청한 포트도 별도 Service로 생성한다.

config-server가 배정한 포트는 스택 DB의 `nodeport_allocations` 테이블에 기록한다. 포트를 고를 때는 이 테이블뿐 아니라 클러스터 전체 Service의 NodePort도 함께 확인한다.

### NodePort와 방화벽 매핑

Kubernetes의 NodePort는 클러스터 안에서 쓰는 포트이고, pfSense는 외부 포트를 이 NodePort로 전달한다. 외부 포트와 NodePort 번호는 같을 필요가 없다. 외부에서 접속하지 못하면 Service의 NodePort와 pfSense의 전달 대상이 같은지 확인한다.

---

### 3.4 Namespace

Namespace는 클러스터 리소스를 용도나 팀별로 구분하는 논리적 공간이다.

이 시스템의 주요 Namespace는 다음과 같다.

| Namespace        | 용도                     |
| ---------------- | ---------------------- |
| `ailab-operation` | 운영 스택 전체: config-server, admin_be, 프론트엔드, DB, 사용자 Pod |
| `ailab-baseline`, `ailab-noprobe`, `ailab-full` | 실험 스택 |
| `ailab-frontend` | ingress 컨트롤러(스택 화면 입구) |
| `ailab-infra`    | 구 운영. 0개로 내려 두었다 |
| `monitoring`     | Prometheus와 Grafana    |

스택 하나가 네임스페이스 하나다. 같은 코드를 이름만 달리해 네 번 띄운다.

리소스를 조회할 때는 Namespace를 정확히 지정해야 한다.

```bash
kubectl get pods -n ailab-operation
```

Namespace를 생략하면 다른 공간의 리소스를 조회하여 장애 원인을 놓칠 수 있다.

---

### 3.5 볼륨, hostPath, subPath

#### hostPath

`hostPath`는 노드 호스트의 특정 파일이나 디렉터리를 컨테이너에 직접 마운트하는 방식이다.

이 시스템에서는 노드에 마운트된 NFS 홈 경로와 Kerberos ccache 경로(`/run/user/<uid>`)에 사용한다.

과거에는 GPU 디바이스(`/dev/nvidia*`)도 hostPath로 개별 마운트했으나, 이 방식은 마운트 시점의 디바이스 파일(inode)에 고정되어 호스트에서 드라이버 리로드 등으로 디바이스가 재생성되면 이미 떠 있는 Pod의 GPU 접근이 복구 불가능하게 끊기는 문제가 있었다. 지금은 노드의 컨테이너 런타임(`nvidia-container-runtime`)이 컨테이너를 만들 때마다 `NVIDIA_VISIBLE_DEVICES`에 적힌 GPU를 붙인다. config-server는 이 값에 **그 노드에서 신청한 종류의 GPU UUID 전부**를 넣는다(GPU 없음은 `void`). GPU를 독점 할당하지 않으므로 같은 GPU를 여러 컨테이너가 함께 쓰고, 다른 종류의 GPU는 보이지 않는다. Pod 스펙의 `volumes`에는 `/dev/nvidia*`가 보이지 않으므로 컨테이너 안에서 `nvidia-smi`로 확인한다.

#### subPath

`subPath`는 볼륨 전체가 아니라 볼륨 안의 특정 파일이나 디렉터리만 골라 마운트하는 옵션이다.

과거에는 `/kube_share/passwd`와 `shadow`를 컨테이너의 `/etc/passwd`, `/etc/shadow`에 직접 마운트했다. 현재 Pod 스펙에는 이 마운트가 없고, config-server가 UID/GID를 환경변수로 전달하면 컨테이너 시작 스크립트가 내부 사용자를 만든다.

코드 주석과 예전 배포 기록에는 `subPath` 방식이 남아 있을 수 있다. 현재 Pod 스펙에는 이 마운트가 없다.

### 3.6 imagePullPolicy와 Ready

#### imagePullPolicy

Pod를 생성할 때 컨테이너 이미지를 어떻게 가져올지 결정하는 정책이다.

| 값              | 동작                     |
| -------------- | ---------------------- |
| `Always`       | Pod 생성 시마다 이미지를 내려받는다. |
| `IfNotPresent` | 노드에 이미지가 없을 때만 내려받는다.  |
| `Never`        | 내려받지 않는다. 노드에 없으면 시작하지 못한다. |

`Always`는 최신 이미지를 보장하지만 시작 시간이 길어질 수 있다. 사용자 Pod는 `IfNotPresent`를 쓴다. 재시작으로 변경분을 구운 이미지는 그 노드에만 있으므로 `Never`를 쓴다.

#### Ready

컨테이너 프로세스가 시작된 상태와 실제 요청을 받을 준비가 된 상태는 다르다.

config-server는 다음 순서로 Pod를 생성한다.

1. Pod 생성 요청을 보낸다.
2. Pod가 Ready가 될 때까지 상태를 확인한다.
3. Ready가 되면 NodePort Service를 만든다.
4. 생성 결과를 응답한다.

NFS 마운트가 실패하여 `FailedMount` 상태가 되면 Pod는 Ready가 되지 않으며, config-server의 대기는 타임아웃으로 종료된다.

---

### 3.7 RBAC와 ServiceAccount

RBAC(Role-Based Access Control)는 Kubernetes 리소스를 누가 다룰 수 있는지 정하는 권한 설정이다.

ServiceAccount는 사람이 아닌 애플리케이션이나 Pod가 사용하는 Kubernetes 내부 신원이다.

### config-server의 Kubernetes 권한

config-server는 자신의 ServiceAccount 권한으로 Kubernetes API를 호출하여 다음 작업을 수행한다.

* Pod 생성과 삭제, Pod 안 명령 실행(비밀번호·그룹 반영)
* Service 생성·삭제·수정(접속 차단·해제)
* Secret 생성과 삭제(keytab, 로그인 비밀번호)
* Pod 상태·이벤트 조회
* 노드 목록과 클러스터 전체 Service 조회

관련 ServiceAccount, Role, ClusterRole은 Helm 차트 배포 과정에서 함께 생성한다.

---

### 3.8 Helm

Helm은 여러 Kubernetes YAML 파일과 설정값을 한 묶음으로 관리하는 도구다.

Deployment, Service, RBAC 등의 정의를 템플릿으로 구성하고, 환경별 값만 변경해 배포할 수 있다.

config-server는 `Chart/` 디렉터리의 Helm 차트로 배포한다. 스택마다 릴리스(`config-server-<스택>`)를 하나씩 두고, Deploy Proposed Stack 워크플로가 설치 스크립트 안에서 `helm upgrade --install`을 실행한다([Helm 차트 레퍼런스](../operations/Helm-차트-레퍼런스.md)).

---

## 4. 모니터링

### 4.1 Prometheus와 Pull 모델

Prometheus는 시스템 지표를 수집하고 저장하는 모니터링 시스템이다.

Prometheus는 각 서버가 데이터를 보내는 push 방식이 아니라, Prometheus가 각 대상의 HTTP 엔드포인트를 주기적으로 조회하는 **pull 방식**을 사용한다.

Prometheus 형식으로 지표를 제공하는 프로그램을 exporter라고 한다.

---

### 4.2 DCGM Exporter

DCGM은 NVIDIA GPU의 상태를 수집하는 도구이며, DCGM exporter는 GPU 지표를 Prometheus 형식으로 제공한다.

config-server는 다음 지표를 노드 선택 점수에 사용한다.

```text
DCGM_FI_DEV_GPU_UTIL
DCGM_FI_DEV_FB_USED
DCGM_FI_DEV_GPU_TEMP
```

### GPU 지표가 없을 때

DCGM exporter가 중단되면 해당 노드의 GPU 지표가 Prometheus에서 사라진다.

현재 쿼리는 값이 없을 때 다음 표현으로 0을 반환한다.

```promql
... or vector(0)
```

이 때문에 지표가 없는 노드를 사용률이 0인 노드, 즉 가장 한가한 노드로 잘못 판단할 수 있다.

> 지표 없음과 실제 사용률 0은 구분해야 한다.

---

### 4.3 PromQL 기본 문법

PromQL은 Prometheus에 저장된 지표를 조회하는 질의 언어이다.

예를 들어 farm5의 GPU 평균 사용률은 다음과 같이 조회한다.

```promql
avg(DCGM_FI_DEV_GPU_UTIL{Hostname="farm5"})
```

주요 문법은 다음과 같다.

| 표현                      | 의미                    |
| ----------------------- | --------------------- |
| `metric{label="value"}` | 특정 레이블을 가진 지표를 조회한다.  |
| `avg(...)`              | 여러 GPU 값의 평균을 계산한다.   |
| `or vector(0)`          | 조회 결과가 없을 경우 0을 반환한다. |

`or vector(0)`은 계산을 단순화하지만, 장애로 인한 지표 부재까지 정상적인 0으로 처리한다는 문제가 있다.

---

### 4.4 Grafana

Grafana는 Prometheus에 저장된 지표를 대시보드 형태로 보여주는 시각화 도구이다.

관리자는 관리 서버의 Grafana NodePort로 노드와 GPU 상태를 확인한다. PromQL을 직접 실행하려면 Prometheus에 port-forward로 접속한다.

---

## 5. 네트워크와 방화벽

### 5.1 공인 IP, 사설 IP, NAT

* **사설 IP**는 내부 네트워크에서만 사용하는 주소이다.
* **공인 IP**는 인터넷에서 직접 접근할 수 있는 주소이다.
* **NAT**는 사설 IP와 공인 IP 사이에서 주소나 포트를 변환하는 기술이다.
* **포트포워딩**은 특정 공인 IP와 포트로 들어온 요청을 내부 서버의 특정 포트로 전달하는 규칙이다.

예시는 다음과 같다.

```text
공인 IP:9300 → farm6:30000
```

---

### 5.2 pfSense

pfSense는 외부 네트워크와 내부 서버 사이에서 방화벽과 라우터 역할을 한다.

공인 주소 두 개를 용도별로 나눠 쓴다.

| 공인 주소 | 정책 |
| --- | --- |
| 관리용 | 사전에 허용한 포트(화면 입구, 관리 도구)만 통과시킨다 |
| 사용자용 | 정해진 외부 포트 구간을 사용자 Pod의 NodePort 구간으로 전달한다 |

사용자용 전달 구간이 정해져 있어서, 운영 스택의 NodePort 대역(30000~30079)은 그 안에 있어야 한다. 구간 밖의 번호를 배정하면 내부에서는 접속되는데 외부에서는 안 되고, 내부 점검으로는 드러나지 않는다.

### 외부 접속이 안 될 때

NodePort 번호만 보고 외부 접속 주소를 추정하지 않는다. Service의 NodePort, pfSense가 전달하는 대상, 사용자에게 안내한 외부 주소를 함께 확인한다.

---

## 6. 저장소와 동시성

### 6.1 트랜잭션과 SELECT ... FOR UPDATE

트랜잭션은 여러 SQL 작업을 하나의 작업 단위로 묶는 기능이다.

트랜잭션 내부의 작업은 모두 성공하거나 모두 취소된다.

`SELECT ... FOR UPDATE`는 조회한 행에 잠금을 걸어, 현재 트랜잭션이 끝날 때까지 다른 트랜잭션이 해당 행을 수정하지 못하게 한다.

### NodePort를 배정하는 순서

NodePort 배정은 다음 순서로 처리한다.

1. 트랜잭션을 시작한다.
2. 사용 중인 포트 목록을 `FOR UPDATE`로 조회한다.
3. 빈 포트를 선택한다.
4. 배정 정보를 insert한다.
5. 트랜잭션을 commit한다.

두 개의 Pod 생성 요청이 동시에 들어오더라도 같은 포트가 중복 배정되는 것을 방지한다.

---

### 6.2 Redis

Redis는 메모리 기반 키-값 저장소이다.

config-server는 스택 Redis에 다음을 둔다.

| 내용 | 보존 |
| --- | --- |
| 작업 입력(제어기가 실행할 값. 비밀번호는 해시만) | 작업이 끝나 결과 행을 남길 때까지 |
| 작업 결과(`result`) | 하루 |
| 생성·이동 진행 상황(`stage`) | 최종 갱신 후 1시간 |

작업 입력을 잃으면 등록된 작업을 실행할 수 없으므로, 이 Redis는 AOF와 RDB로 디스크에 영속화한다. 다시 떠도 대기 중인 작업 입력이 돌아온다.

---

### 6.3 정보별 기준 저장 위치

같은 정보가 여러 곳에 있으면 값이 달라질 수 있다. 그래서 정보마다 어느 곳의 값을 기준으로 사용할지 정해 둔다.

이 시스템에서는 다음 위치의 값을 기준으로 사용한다.

| 정보          | 기준으로 보는 곳                             |
| ----------- | --------------------------------------- |
| 사용자 UID/GID | `/kube_share/passwd`                    |
| 요청 상태       | admin_be DB의 `requests` 테이블             |
| NodePort 배정 | `pod_port_db`의 `nodeport_allocations` 테이블 |
| 작업 진행·결과 | `operation_state_db`의 `operation_log` 테이블 |
| 예약 계정 이름 | config-server의 `GET /reserved-names` (admin_be는 캐시) |

admin_be가 config-server에 UID를 전달하더라도 config-server는 전달값을 신뢰하지 않고 `/kube_share/passwd`를 기준으로 동작한다.

반대로 요청의 `PENDING`, `FULFILLED`, `DELETED` 상태는 admin_be가 관리하며 config-server는 해당 상태를 저장하지 않는다.

---

### 6.4 삭제 표시(soft delete)

삭제 표시는 데이터베이스 행을 지우지 않고 삭제되었다는 상태만 기록하는 방식이다.

admin_be의 요청 상태 `DELETED`가 이에 해당한다.

주요 장점은 다음과 같다.

* 삭제 이력을 보존한다.
* 운영 감사와 장애 추적이 가능하다.
* 필요할 경우 데이터를 복구할 수 있다.

---

## 7. 실행 환경

### 7.1 Flask와 Gunicorn

Flask는 config-server에 사용한 Python 웹 프레임워크이다.

Flask의 내장 서버는 개발용이므로 운영 환경에서는 Gunicorn을 사용한다. Gunicorn은 여러 워커 프로세스로 Flask 애플리케이션을 실행하여 동시 요청을 처리한다.

API 서버는 Gunicorn 워커 4개로 돌고, 제어기는 Gunicorn 없이 `python controller.py`로 따로 돈다. 계정 파일을 바꾸는 쪽은 주로 제어기지만, 등록 경로(계정 이어받기)도 대장을 고치므로 둘 사이의 순서는 DB 잠금으로 맞춘다(2.3절).

---

### 7.2 WAS와 Spring Boot

WAS(Web Application Server)는 웹 요청을 받아 비즈니스 로직을 실행하는 서버를 의미한다.

이 시스템에서는 Spring Boot로 작성한 `admin_be`가 WAS 역할을 수행한다.

운영 문서나 대화에서 “WAS”라고 표현하면 일반적으로 `admin_be`를 의미한다.

---

### 7.3 Swagger

Swagger는 API 목록과 요청 형식을 웹 페이지로 제공하고, 브라우저에서 직접 API를 호출할 수 있게 하는 도구이다.

config-server Swagger는 `/apidocs/`에 있다. API 문서도 경로와 요청 형식이 드러나므로 내부 API 토큰(`X-Internal-Token`)이 있어야 열린다.

### Swagger를 사용할 때

config-server API에는 사용자 인증이 없고, admin_be와 나눠 가진 내부 토큰 하나로만 호출자를 확인한다. 토큰을 가진 사람은 모든 작업을 등록할 수 있다.

따라서 Swagger의 `Try it out` 기능은 단순한 테스트가 아니라 실제 Kubernetes와 NAS 리소스를 생성·수정·삭제할 수 있는 운영 명령이다.

> Swagger 호출은 실제 인프라를 변경하는 작업이므로 운영 권한과 동일하게 취급해야 한다.

---

## 핵심 구조 요약

여기서는 다음 방식으로 동작한다.

1. 사용자 식별과 파일 권한의 기준은 UID/GID이다.
2. UID/GID는 `/kube_share/passwd`에 적힌 값을 사용한다.
3. 사용자 홈은 NFS에 저장하며 `chmod 711`과 컨테이너 `umask 007`로 다른 사용자의 접근을 막는다.
4. `root_squash` 때문에 사용자 홈은 Pod 생성 전에 NAS에서 미리 생성해야 한다.
5. 승인된 신청 하나당 하나의 Pod와 여러 NodePort Service를 생성한다.
6. 실행 노드는 config-server가 Prometheus GPU 지표를 바탕으로 선택한다.
7. NodePort는 스택 DB(`pod_port_db`)에서 트랜잭션과 행 잠금으로 배정한다.
8. 외부 접속은 pfSense가 외부 포트를 해당 NodePort로 전달해야 가능하다.
9. NAS, 계정 파일, NodePort DB 등 주요 기준 정보가 손상되면 전체 시스템에 영향을 줄 수 있다.
10. config-server API는 내부 API 토큰(`X-Internal-Token`)으로만 변경할 수 있다. 토큰은 실제 인프라를 바꾸는 권한이므로 Secret에만 두고 문서·로그에 남기지 않는다.
