# 무결성·정합성 점검 (2026-09-26)

## 이 문서에서 다루는 내용

- 신청 → 작업 등록 → 제어기 실행 → 결과 반영 흐름에서 **사용자 입장**과 **시스템 입장**의 무결성이 깨지는 지점
- 그 결과 남는 **고아 자원**의 종류와, 그것을 누가 판정하는지
- 정합성·멱등성·안정성·보상 트랜잭션 관점의 현재 설계와 빈틈
- 책임이 불명확한 아키텍처 경계

근거는 `admin_be`(develop `5a01e7f`), `admin_infra-proposed` config-server(develop `823417f`) 코드다.
"재현"이라고 적은 항목은 config-server 가상 E2E 테스트 틀(`tests/test_e2e_virtual.py`의 `env`)로
실제 단계 함수를 돌려 확인했다. "코드 경로"라고 적은 항목은 코드를 따라가 확인했지만 실행해 보지는 않았다.

## 2. 책임 경계

| 영역 | 저장소 | 맡는 일 | 맡지 않는 일 |
| --- | --- | --- | --- |
| 신청 상태 | `admin_be` | 신청 상태 전이, 작업 등록, 결과 반영, 사용자·관리자 통보 | 인프라 자원을 직접 만들거나 지우기 |
| 실행·보상 | `admin_infra-proposed` config-server | 단계 실행, 재시도, 이어하기, 실패 시 자기 작업이 만든 자원 되돌리기 | 신청 상태 판단 |
| **판정** | `admin_infra_server` | DB 기록과 실제 인프라(Kubernetes·NAS·노드)를 대조해 어긋난 자원을 찾아냄 — 고아 후보 점검(`infra-integrity-check`, 작업 중), 노드 설정 점검(server-state), 모니터링 경보 | 신청·작업 상태 변경 |

고아 자원을 **찾아내는** 일은 system 영역(`admin_infra_server`)이 맡는다. `admin_be`나 config-server에 별도 재조정기를 만들지 않는다.
이 문서의 결함은 고아를 **만들어 내는 원인**이며, 원인은 해당 코드 저장소에서 고친다. 4절의 표는 판정 쪽이 점검 기준을 넓힐 때 쓸 입력이다.

## 3. 결함 상세

### 3.1 사용자 입장 무결성

사용자가 보는 것(신청 상태, 안내 메일, 화면의 포트)과 실제 자원이 일치하는지를 본다.

#### U1. 사용 중이거나 처리 중인 신청을 거절하면 컨테이너가 남는다

- **위치:** `admin_be` `AdminRequestCommandService.rejectRequest` — PENDING·PROCESSING·FULFILLED를 모두 받아 `Request.reject()`로 DENIED만 기록한다. 회수 작업을 등록하지 않는다.
- **FULFILLED 거절:** Pod·Service·NodePort·계정이 그대로 살아 있다. 사용자에게는 "거절" 메일이 가는데 컨테이너는 계속 접속된다. DENIED는 만료 대상(`FULFILLED`만 조회)에서 빠지고, 고아 Pod 삭제(`deleteOrphanPod`)는 신청에 Pod 이름이 남아 있어 `POD_NOT_ORPHAN`으로 막힌다 — **어떤 화면 경로로도 지울 수 없다.**
- **PROCESSING 거절:** 도는 중인 생성 작업은 계속 진행되고, 끝난 결과는 `completeApprovalJob`이 "상태가 바뀌었다"며 버린다. 같은 결과다.
- `Request.delete()`는 PROCESSING 삭제를 "고아 계정/Pod가 생긴다"며 막고 있다. 같은 이유가 거절에는 적용되지 않았다.
- **재발 방지:** 거절은 PENDING에서만 허용한다. 사용 중인 컨테이너를 끝내는 것은 이미 있는 "컨테이너 회수"(`DELETE /api/admin/requests/{id}/container`)로 보낸다.

#### U2. 계정을 회수당한 사용자는 다시 컨테이너를 받을 수 없다

- **흐름:** 비활성화(`deactivateUser`)나 계정 회수는 원장 계정을 지우고 홈은 보존한다(옛 uid 소유). 재활성화 뒤 다시 신청해 승인하면 `admin_be`는 옛 uid를 `expected_uid`로 보내지만, config-server는 **원장에 같은 이름·같은 uid 계정이 있을 때만** 이어받는다(`_adoptable_account_uid`). 원장에는 없으므로 새 uid를 발급하고(#201로 옛 번호는 재발급하지 않는다), 홈 생성 단계가 "이미 있는 홈의 소유자가 다르다"로 멈춘다.
- **재현:** 생성 → `delete_account` 회수 → `expected_uid`를 담아 다시 생성 → `FAIL HOME_OWNER_MISMATCH`. 재승인해도 매번 같다.
- **영향:** 사용자 데이터는 안전하지만(덮어쓰지 않음), 관리자가 NAS에서 소유자를 직접 바꾸기 전에는 서비스를 받을 수 없다. 관리자에게는 "생성 작업 실패" 알림만 간다.
- **재발 방지:** 옛 uid와 홈 소유자가 일치하면 그 uid를 다시 쓰는 규칙이 필요하다. 이는 "지워진 번호는 다시 주지 않는다"(#201)는 원칙과 충돌하므로, **같은 사람에게 같은 번호를 돌려주는 경우만 예외**로 두는 설계 결정이 먼저다.

#### U3. 마이그레이션 뒤 포트 변경을 사용자에게 알리지 않는다

- **위치:** `PodMigrationService.completeMigrationJob` — 새 Pod의 포트로 `pod_external_ports`를 바꾸고 관리자 알림만 보낸다.
- 외부 접속 포트는 NodePort에서 계산되므로 새 NodePort가 배정되면 사용자의 SSH 설정이 끊긴다. 화면에서는 새 포트가 보이지만 사용자가 알아챌 계기가 없다.
- **재발 방지:** 생성 때 쓰는 안내 메일과 같은 형식으로 변경 안내를 보낸다.

### 3.2 시스템 입장 무결성

기록(`admin_be` DB, `operation_log`, 원장, AD, Kubernetes, NAS)끼리 서로 맞는지를 본다.

공통 원인: config-server의 몇몇 단계는 실패하면 **그 단계 안에서** 앞선 자원을 되돌린 뒤 예외를 던진다. 그런데 작업 실행기(`application/jobs.py` `_execute_step`)는 5xx 실패를 같은 단계로 재시도한다. 앞 단계는 "끝남"으로 기록돼 다시 돌지 않으므로, 재시도는 **이미 지워진 자원을 전제로** 실행된다.

#### S3. Service 생성 일시 오류 → Pod 없이 작업 성공 (치명)

- **위치:** `lifecycle_steps/provision.py` `step_create_services` — 예외 시 `_cleanup_create_failure(..., delete_services=True)`로 Service·포트 배정 기록·Pod를 지우고 500(재시도 가능)을 던진다.
- **재현:** Service 생성이 한 번만 실패하게 두면 → Pod 삭제·포트 배정 반환 → 재시도에서 사전 정리 후 Service를 **같은 포트로 다시 만들고** 성공 → 작업 `SUCCESS`, 결과에 포트 두 개, Pod 0개.
- **영향:** `admin_be`는 FULFILLED로 확정하고 사용자에게 접속 포트를 메일로 안내한다. 실제로는 Pod가 없다. 포트 배정 기록이 반환됐으므로 다음 배정이 같은 번호를 고를 수 있다(클러스터 Service 조회가 막아 주지만, 그 조회가 실패하면 기록만 본다).
- **재발 방지:** Pod를 지운 실패는 `retry=False`로 던진다. `step_wait_ready`의 시간 초과 경로는 이미 같은 이유로 `retry=False`다 — 나머지 예외 경로에 같은 규칙을 적용한다.

#### S2. Ready 확인 중 API 일시 오류 → 거짓 DEGRADED

- **위치:** `step_wait_ready`의 `ApiException`·일반 예외 경로 — Pod를 지운 뒤 재시도 가능한 500을 던진다.
- **재현:** Ready 확인이 한 번 500을 내면 → Pod 삭제 → 재시도 두 번 모두 "Pod 없음" → `RETRIES_EXHAUSTED` → 작업 `FAIL DEGRADED`. 원장에는 계정이 남아 있다.
- **영향:** `admin_be`는 DEGRADED를 "자원을 남긴 실패"로 보고 신청을 PROCESSING에 둔 채 알림만 보낸다. 실제로 남은 것은 Pod가 아니라 계정뿐이다. 신청은 사람이 풀어 줄 때까지 갇힌다.
- **재발 방지:** S3와 같다.

#### S1. 홈·Kerberos 단계의 자체 되돌림 + 재시도

- **위치:** `step_create_home`(NAS 오류 시 `_rollback_user`), `step_create_krb5_principal`(KDC 오류 시 홈 삭제·AD principal 삭제·`_rollback_user`).
- **재현(홈 단계 일시 오류):** 계정 생성 → 홈 실패·계정 되돌림 → 홈 재시도 성공 → **원장에 없는 계정으로** Kerberos principal 생성 → Pod 스펙 단계 `user not found in /etc/passwd` → 작업 보상이 계정 삭제에서 `USER_NOT_FOUND`로 멈춰 뒤의 Kerberos 정리를 건너뜀 → 최종 `FAIL POD_SPEC_BUILD_FAILED`.
- **남는 것:** AD principal, keytab Secret(`krb5-keytab-<사용자>`), NAS 홈 디렉터리.
- **오류 코드:** 실제 원인(NAS 일시 오류)이 `POD_SPEC_BUILD_FAILED`로 가려진다.
- **추가 위험:** Kerberos 실패 되돌림은 홈을 `rm -rf`로 지운다. 이 홈이 **이번 작업이 만든 것인지** 확인하지 않는다. 작업 보상(`_compensate_provision`)은 "이전 회수에서 보존된 같은 이름의 홈일 수 있다"며 홈을 지우지 않는데, 단계 안의 되돌림은 반대로 동작한다. 지금은 uid 불일치 검사가 대부분 막아 주지만, 두 규칙이 서로 모순이다.
- **재발 방지:** 단계는 자기 효과만 되돌리고(홈 단계는 홈만), 계정 되돌리기는 작업 보상 한 곳에서만 한다. 작업 보상은 이미 없는 계정(`USER_NOT_FOUND`)을 성공으로 보고 다음 정리를 계속한다.

### 3.3 결과 반영 경계

#### M1. 마이그레이션 성공 결과가 없으면 "건너뜀"으로 처리

- **위치:** `PodMigrationService.completeMigrationJob` — `made == null`이면 Pod 정보를 바꾸지 않고 `endMigration()`한다.
- config-server는 결과(`result`)를 하루만 보관한다. `admin_be`가 그보다 오래 멈춰 있었다면(축소·장애) 성공한 마이그레이션의 결과가 비어 온다. 신청은 옛 Pod 이름으로 FULFILLED가 되고 새 Pod는 추적되지 않는다. 만료 때 옛 Pod 회수는 "이미 없음"으로 성공해 신청이 DELETED가 되고, 새 Pod는 계속 돈다.
- 생성 경로(`completeApprovalJob`)는 같은 상황을 "사람이 확인하도록 멈춤"으로 막고 있다.
- **재발 방지:** 생성 경로와 같이 결과가 없으면 반영하지 않는다. 근거가 필요하면 `/operations/migrate/{id}/steps`의 단계 기록에서 새 Pod 이름을 읽는다.

#### P1. 생성 성공 결과가 없으면 같은 알림이 3초마다 반복

- **위치:** `ProvisionJobPoller` → `completeApprovalJob(made == null)` — 상태를 그대로 두고 알림을 보낸 뒤 돌아온다. 폴러는 PROCESSING 전체를 3초마다 다시 보므로 같은 알림이 계속 간다. 결과 불명·DEGRADED에는 있는 "한 번만 알림"(`reportedUnknown`)이 이 경로에는 없다.
- 알림 대상은 승인 판단에 쓰는 FARM/LAB 관리자 채널이다.
- **재발 방지:** 같은 중복 억제를 이 경로에도 적용한다.

#### I1. 작업 등록 응답을 받지 못하면 곧바로 되돌린다

- **위치:** `approveRequest` → `registerProvision` 예외 시 `revertToPendingIfStillProcessing`.
- 등록 요청이 config-server에 도착해 작업이 저장된 뒤 응답만 늦으면(타임아웃·연결 끊김), 신청은 PENDING이 되고 작업은 계속 돈다. 폴러는 PROCESSING만 보므로 그 결과를 반영하지 않는다. 계정 기록도 채워지지 않아, 재승인은 계정 생성부터 다시 하려다 실패한다.
- 409(같은 신청의 작업이 진행 중)만 "등록돼 있음"으로 구분하고, 그 밖의 오류는 전부 "등록 안 됨"으로 본다.
- **재발 방지:** 등록 실패 시 되돌리기 전에 `GET /operations/provision/{id}`로 방금 등록된 작업이 있는지 확인하고, 있으면 PROCESSING을 유지하고 작업 번호를 기록한다.

## 4. 고아 자원 — 판정 기준 입력

고아의 판정은 `admin_infra_server`가 맡는다(2절). 아래는 3절의 결함이 만드는 고아를 종류별로 모은 것이다.
"현재 점검 범위"는 `infra-integrity-check` 작업 브랜치의 README 기준이다(DB status가 DELETED인 신청의 Pod, 배정 기록 없는 NodePort Service, 삭제 사용자 홈).

| 남는 자원 | 만드는 결함 | 알아볼 수 있는 근거 | 현재 점검 범위 |
| --- | --- | --- | --- |
| 살아 있는 Pod·Service (신청은 DENIED) | U1 | `requests.status = DENIED`인데 `pod_name`의 Pod가 존재 | 없음 (DELETED만 봄) |
| 살아 있는 Pod (어느 신청도 가리키지 않음) | M1, I1 | 사용자 Pod 라벨이 있는데 `requests.pod_name`에 없음 | 없음 |
| Pod 없는 NodePort Service | S3 | `app=ailab-nodeport` Service의 `pod_name` Pod가 없음 | 부분 (배정 기록이 없을 때만) |
| AD principal·keytab Secret (원장에 계정 없음) | S1 | `krb5-keytab-<이름>` Secret은 있는데 원장에 그 이름이 없음 | 없음 |
| NAS 홈 (원장·DB 모두 없음) | S1 | 홈 디렉터리 이름이 원장·`requests` 어디에도 없음 | 부분 (`NO_DB_MATCH`로 표시만) |
| 원장 계정 (DB에 uid 기록 없음) | S2, I1 | 원장 사용자의 uid가 `users.ubuntu_uid`에 없음 | 없음 |

판정 결과로 **무엇을 고칠지**(누가, 어떤 경로로 정리하는지)는 아직 정해져 있지 않다 — 5.4 참고.

## 5. 정합성·멱등성·안정성·보상 트랜잭션

### 5.1 멱등성

| 동작 | 현재 | 빈틈 |
| --- | --- | --- |
| 작업 등록 | (작업 종류, 신청 번호)마다 끝나지 않은 작업은 하나만 — 두 번째는 409 | 응답 유실 시 재요청으로 같은 결과를 돌려받는 키가 없음(I1) |
| 단계 실행 | 결과 불명이면 실제 상태를 먼저 확인(계정·principal·Pod), 재실행 안전 단계 목록 | 자체 되돌림 단계는 재실행이 안전하지 않은데 재시도됨(S1~S3) |
| 회수 | 이미 없는 Pod·계정은 성공으로 봄 | 작업 보상은 `USER_NOT_FOUND`에서 멈춤(S1) |
| 끝난 작업 재선택 | 끝 행 확인(`job_end_exists`)으로 건너뜀 | — |

### 5.2 정합성 (상태 전이)

- `admin_be`는 행 잠금 + 상태 재확인으로 전이를 보호한다: 승인(PENDING→PROCESSING), 만료·회수(FULFILLED→EXPIRING 선점), 결과 반영(PROCESSING일 때만). 거절(U1)만 이 규칙 밖에 있다.
- 작업 결과는 신청 번호로만 조회된다. 재승인 직후 이전 작업 결과를 읽지 않도록 작업 번호 대조(`isFromOtherJob`)와 등록 대기(`awaitingRegistration`)를 둔다.
- 신청 DB가 초기화돼 번호가 다시 쓰이면 옛 작업과 섞인다. 단계 기록 화면은 생성 시각으로 거르지만, 결과 폴러는 작업 번호가 기록된 뒤에만 보호된다.

### 5.3 안정성

- 제어기는 lease로 작업 소유권을 잡고, 죽으면 다른 제어기가 끝난 단계 다음부터 이어간다.
- 결과 행 기록이 실패하면 입력을 "done"으로 남겨 다음 바퀴에 결과 행만 다시 쓴다.
- 결과(`result`)는 하루만 보관된다. `admin_be`가 그보다 오래 멈추면 성공 결과를 반영할 근거가 사라진다(M1, P1). 단계 기록(`operation_log`)은 남으므로 근거를 거기서 다시 얻을 수 있다.
- 관리자 컨테이너 회수는 HTTP 요청 안에서 회수 완료까지 기다린다(기본 최대 900초, `operations.revoke.timeout-seconds`). 앞단 프록시의 제한 시간이 더 짧으면 관리자는 오류를 보지만 회수는 계속된다.

### 5.4 보상 트랜잭션

| 실패 지점 | 누가 되돌리나 | 결과 |
| --- | --- | --- |
| 작업 등록 실패 | `admin_be` | PENDING으로 되돌림 (I1의 빈틈) |
| 계정 단계 안 | 그 단계 | 원장 되돌림 — 다만 재시도와 겹침(S1) |
| 계정 이후 단계 | config-server 작업 보상 | 같은 사용자의 다른 Pod가 있거나 노드를 모르면 보류(`held`) |
| Pod·Service 단계 | 그 단계 | Pod·Service·포트 정리 — 다만 재시도와 겹침(S2, S3) |
| 재시도 소진·판정 불능 | 되돌리지 않음(DEGRADED/UNKNOWN) | `admin_be`는 PROCESSING 유지 + 알림 |
| 만료·회수 실패 | `admin_be` | EXPIRING→FULFILLED로 되돌려 다음 회차 재시도 |

보상이 멈추거나 보류된 경우의 **유일한 신호는 Slack 알림**이다. 신청 화면이나 DB에는 "관리자 확인 필요" 표시가 남지 않는다. 결과 불명 알림을 한 번만 보내기 위한 기록(`reportedUnknown`)도 메모리에만 있어 재시작하면 다시 보낸다.

## 6. 유지해야 할 설계

고칠 때 깨지 않아야 할, 이미 잘 동작하는 규칙이다.

- 외부 호출 동안 DB 행 잠금·커넥션을 잡지 않는다(짧은 트랜잭션 → HTTP → 짧은 트랜잭션).
- 상태를 먼저 선점(EXPIRING·PROCESSING)한 뒤 외부 작업을 하고, 끝나면 다시 잠가 상태를 재확인한다.
- 결과가 불명확하면 되돌리지 않는다(UNKNOWN·DEGRADED). 되돌리면 자원이 남은 채 재승인으로 중복 생성된다.
- 계정을 지울 노드를 모르면 지우지 않고 보류한다. 잘못 지운 남의 계정은 되돌릴 수 없다.
- 이미 있는 홈·팀 디렉터리의 소유자가 다르면 덮어쓰지 않는다.
- 회수 때 홈은 보존한다.

## 7. 불명확한 아키텍처

| # | 내용 | 정해야 할 것 |
| --- | --- | --- |
| A1 | 사실의 원본이 다섯 곳(신청 DB, `operation_log`, 원장, AD, Kubernetes·NAS)에 흩어져 있고, 서로 어긋났을 때 **어느 쪽이 맞는지** 정한 규칙이 없다 | 자원별 원본 지정(예: 계정 존재는 원장, 배치는 Kubernetes) |
| A2 | 판정(`admin_infra_server`)이 어긋남을 찾은 뒤 **누가 어떤 경로로 고치는지**가 없다 — 지금은 DB 직접 수정 | 판정 결과를 받아 정리하는 정식 경로와 담당 |
| A3 | DEGRADED·UNKNOWN으로 멈춘 신청을 푸는 절차가 문서에 없다. `admin_be`는 PROCESSING에 두고 config-server 몫으로 넘긴다 | config-server 쪽 해소 절차(재등록·수동 정리) 문서화 |
| A4 | 되돌리기가 두 층(단계 안 + 작업 보상)에 나뉘어 있고 규칙이 다르다(홈 삭제 여부, 계정 되돌림 위치) | 되돌리기는 작업 보상 한 곳, 단계는 자기 효과만 |
| A5 | 작업 식별자가 `admin_be` 신청 번호에 묶여 있다. 신청 DB가 초기화되면 옛 작업과 섞인다 | 작업 번호를 1차 식별자로 쓰는 조회 |
| A6 | 장애·보상 실패 알림이 승인 판단용 FARM/LAB 채널로 간다 | 장애 알림을 받을 경로와 채널 |

## 8. 권장 순서

1. **S3·S2·S1** (config-server) — Pod·계정을 지운 실패는 재시도하지 않게 하고, 계정 되돌리기를 작업 보상 한 곳으로 모은다. 가상 E2E 테스트에 "한 번만 실패하는 외부 호출" 시나리오를 추가한다.
2. **U1** (admin_be) — 거절을 PENDING으로 제한한다.
3. **M1·P1** (admin_be) — 결과가 없을 때의 처리를 생성·마이그레이션에서 같게 맞추고 알림 중복을 막는다.
4. **I1** (admin_be) — 등록 실패 시 되돌리기 전에 등록 여부를 조회한다.
5. **U2** — uid 재사용 예외 규칙을 먼저 결정한 뒤 구현한다.
6. **4절 표**를 `admin_infra_server` 판정 기준 논의에 넘긴다.
