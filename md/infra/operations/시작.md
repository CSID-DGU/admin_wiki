## 1. 브랜치와 배포

네 저장소(admin_fe·admin_be·admin_infra·admin_infra-proposed)가 같은 규칙을 쓴다 — [브랜치·배포 규칙](../../브랜치-규칙.md).

- 브랜치는 `main` 하나다. `main`에서 `<커밋 타입>/v<버전>-<짧은 설명>` 브랜치를 따서(예: `fix/v3.3-returning-user-uid`) PR로 `main`에 squash 병합한다.
- PR은 CI(테스트) 통과가 필요하다.
- 어느 브랜치에 push해도 자동 배포는 없다. 배포는 admin_infra의 Deploy Proposed Stack 워크플로로만 한다.
- 실험 스택은 `main`이나 작업 브랜치를, 운영(operation)은 네 저장소에 같은 이름으로 찍은 릴리스 태그 `vX.Y.Z`만 배포한다.

config-server 코드는 **admin_infra-proposed**에 있다. admin_infra에는 배포 워크플로와 구 운영 시절 코드가 남아 있다.

## 2. 로컬에서 시험하기

### 2.1 단위 테스트

PR마다 CI가 같은 명령을 돌린다.

```bash
cd admin_infra-proposed
pip install -r config-server/requirements.txt pytest
pytest config-server
(cd harness && pytest)
```

config-server 테스트에는 실제 단계 함수를 가짜 Kubernetes·NAS·AD로 돌리는 가상 E2E(`tests/test_e2e_virtual.py`)가 있다. 실패·재시도·이어하기 같은 경로는 여기서 먼저 재현한다.

`harness/test_e2e_catalog.py`는 admin_be의 생명주기 전이 표와 config-server의 모든 오류 코드가 E2E 카탈로그(`harness/e2e/catalog.yaml`)의 사례·시험·면제 중 하나에 있는지 확인한다. 새 오류 코드를 만들면 이 테스트가 실패하므로 카탈로그에 함께 넣는다.

### 2.2 로컬에서 띄워 보기

config-server는 Python 3.10 slim과 gunicorn으로 만든 컨테이너로 실행한다.

```bash
cd admin_infra-proposed/config-server
docker build -t config-server:local .
docker run --rm -p 8000:8000 -e CONFIG_API_AUTH_DISABLED=true config-server:local
```

- 상태 확인: `http://localhost:8000/health`
- Swagger: `http://localhost:8000/apidocs/`

`CONFIG_API_AUTH_DISABLED=true`는 로컬 개발에서만 토큰 검사를 끈다. 배포에는 이 값을 넣지 않는다. 작업 실행은 Kubernetes API, MySQL, Redis, `/kube_share` NFS, NAS·AD SSH가 있어야 하므로 로컬에서는 Swagger와 입력 검증까지만 확인하고, 실제 동작은 실험 스택에서 확인한다.

## 3. 실험 스택에서 확인하기

실험 스택(`ailab-noprobe`, `ailab-full`, `ailab-baseline`)은 operation과 같은 구성이고 UID·포트 대역과 계정 접두어만 다르다. 작업 브랜치를 실험 스택에 올려 확인한다.

```bash
gh workflow run deploy-proposed-stack.yaml -R CSID-DGU/admin_infra \
  -f stack=noprobe -f ref=<작업 브랜치> -f be_ref=main -f fe_ref=main
```

실험 스택의 계정 이름은 반드시 스택 접두어(`exp-np-`, `exp-fu-`, `exp-bl-`)로 시작해야 한다. AD·Kerberos, NAS 홈, FARM 노드를 운영과 같이 쓰고 이름으로 구분하기 때문에, config-server가 접두어 없는 이름을 거절한다.

신청 생명주기 전 사례는 E2E 도구로 돌린다.

```bash
python -m harness.e2e list                                 # 사례 목록
python -m harness.e2e run --stack full                     # 장애 없는 사례
python -m harness.e2e run --stack full --allow-faults      # Pod 사망·NAS/AD 차단·config-server 중단 포함
python -m harness.e2e run --stack full --case C04 --keep   # 한 사례만, 정리하지 않고 남김(조사용)
python -m harness.e2e reset --stack full --run <runid>     # 남겨 둔 실행 정리
```

접속 정보는 저장소 밖 `~/.ailab-exp/e2e.env`에 둔다. 사례마다 새 사용자를 만들고, 끝나면 이번 실행이 만든 것을 전부 지운 뒤 남은 것이 있으면 실패로 끝난다. operation에서는 실행·정리를 모두 거부한다.

```bash
# 배포된 config-server 확인
kubectl -n ailab-noprobe get pods -l app=containerssh-config-server
kubectl -n ailab-noprobe logs deploy/config-server-noprobe-controller --since=10m
```

## 4. 커밋과 PR

[브랜치·배포 규칙](../../브랜치-규칙.md)의 1·2절을 따른다. 커밋 메시지는 Conventional Commits(`fix: …`) 형식이다.

- 저장소가 공개라 Actions 로그를 누구나 본다. 스크립트·워크플로가 비밀번호, 운영 설정값, 실사용자 계정 이름, 인프라 주소를 출력하지 않게 한다.
- 테이블 구조를 바꾸면 `infra-sql/`의 SQL 파일에 반영한다. 운영 DB를 손으로 고치지 않는다.
- 스택 대역을 바꾸면 `ops/proposed-stack/uid-ranges.yaml`만 고친다.
