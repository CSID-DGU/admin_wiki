# 개요

## 이 문서에서 다루는 내용

- config-server가 전체 시스템에서 맡는 역할
- 승인 뒤 계정, 홈 디렉터리, Pod, NodePort가 만들어지는 큰 흐름
- 관련 저장소와 배포 위치

문서를 어디서부터 읽어야 할지 찾고 있다면 [infra 목차](index.md)를 먼저 보고, 이 페이지는 config-server 자체가 무슨 역할을 맡는지 이해하는 데 집중하면 된다.

## 1. config-server가 하는 일

DECS는 연구실 GPU 서버를 웹에서 신청하고 승인받아 사용하는 시스템이다. 세 서버가 다음 일을 나눠 한다.

| 서버 | 하는 일 |
|------|----------|
| admin_fe | 사용자와 관리자가 신청과 승인 결과를 확인하는 화면을 제공한다. |
| admin_be | 신청 내용과 승인 상태를 저장하고 config-server에 작업을 등록한다. |
| **config-server** | 계정, 홈 디렉터리, Pod, 접속 포트를 만들거나 바꾸거나 지운다. |

admin_be가 승인 여부를 정하고, config-server가 Kubernetes·NAS·AD에 실제 작업을 수행한다. config-server는 스스로 사용자를 승인하지 않고, 보존 기간이 지났는지 같은 판단도 하지 않는다. "지금 해도 되는 상태인가"만 확인한다.

config-server는 두 프로세스로 나뉜다.

| 프로세스 | 하는 일 |
|------|----------|
| API 서버 | admin_be의 요청을 검사해 **작업으로 등록**하고 바로 202로 답한다. 결과·진행 상황 조회도 받는다. |
| 제어기(controller) | 등록된 작업을 꺼내 단계별로 실행하고, 단계마다 결과를 작업 이력에 남긴다. |

등록과 실행을 나눈 이유는 Pod 하나를 만드는 데 이미지 다운로드까지 몇 분이 걸리기 때문이다. 요청 하나가 그동안 연결을 쥐고 기다리면 배포·재시작 때 끊긴 요청의 결과를 알 수 없다. 작업으로 남겨 두면 제어기가 다시 떠도 남은 단계부터 이어서 처리한다.

## 2. 승인 뒤에 일어나는 일

```mermaid
flowchart LR
    A[사용자<br/>웹에서 신청] --> B[관리자<br/>승인 버튼]
    B --> C["config-server<br/>계정·홈·컨테이너·포트 생성"]
    C --> D[사용자에게<br/>접속 안내 메일]
    D --> E[만료되면<br/>컨테이너·계정 회수]
    E --> F[보존 기간이 지나면<br/>홈 삭제]
```

관리자가 승인하면 config-server는 다음 순서로 작업한다.

1. **계정 만들기** — 리눅스 계정(UID)을 공용 계정 파일에 등록하고 AD에도 같은 번호로 만든다.
2. **홈 폴더 만들기** — NAS(공용 저장 장비)에 그 사용자의 홈 디렉터리를 만든다.
3. **GPU Pod 만들기** — 신청한 GPU 종류가 있고 사용량이 낮은 노드를 골라 Pod를 만든다.
4. **접속 포트 열기** — SSH·Jupyter와 신청한 추가 포트마다 접속 포트를 배정한다.
5. **결과 전달** — admin_be가 작업 결과에서 Pod 이름과 포트를 읽어 사용자에게 안내 메일을 보낸다.

만료되면 Pod와 포트를 지운 뒤 계정을 정리한다. 홈 디렉터리는 회수 때 지우지 않고, admin_be가 정한 보존 기간이 지난 뒤 별도 작업으로 지운다.

생성·회수 말고도 다음 일을 작업으로 받는다.

| 작업 | 언제 쓰나 |
|------|----------|
| 마이그레이션·재시작 | 컨테이너를 다른 노드로 옮기거나 같은 노드에서 다시 만들 때 |
| 비밀번호 교체 | 비밀번호 재설정 신청이 승인됐을 때 |
| 그룹 | 공용 그룹을 만들거나 사용자를 넣고 뺄 때 |
| 포트 변경 | 떠 있는 컨테이너의 추가 포트를 바꿀 때 |
| 접속 차단·해제 | 이용 정지된 계정의 모든 접속 포트를 막거나 풀 때 |
| 홈 삭제 | 보존 기간이 지난 홈을 지울 때 |

## 3. config-server가 없을 때 하던 일

이 시스템이 없던 때에는 관리자가 서버에 접속해 계정·컨테이너·포트를 모두 명령어로 처리했다.

- 신청이 몰리면 **관리자 한 사람이 병목**이 된다.
- UID 중복·포트 충돌 같은 **수작업 실수**가 발생한다.
- 만료된 자원을 사람이 기억해 삭제해야 하므로 **GPU가 방치**될 수 있다.

config-server는 이 작업을 API로 처리한다. 계정, GPU 노드, 포트가 정해지는 방법은 [시스템 아키텍처](design/시스템-아키텍처.md)에 있다.

## 4. 저장소 구성

코드는 두 저장소에 나뉘어 있다.

| 저장소 | 내용 |
|----------|------|
| [`CSID-DGU/admin_infra-proposed`](https://github.com/CSID-DGU/admin_infra-proposed) | **운영과 실험 스택이 실제로 쓰는 코드.** config-server, 스택 설치 스크립트, E2E 시험 도구 |
| [`CSID-DGU/admin_infra`](https://github.com/CSID-DGU/admin_infra) | 배포 워크플로(Deploy Proposed Stack)와 구 운영 시절 코드 |

`admin_infra-proposed` 안의 디렉터리는 다음과 같다.

| 디렉터리 | 내용 |
|----------|------|
| `config-server/` | Flask API 서버·제어기와 Helm 차트 |
| `infra-sql/` | 포트 배정·작업 이력 테이블 정의(SQL) |
| `ops/proposed-stack/` | 스택 설치·제거 스크립트(`stack-up.sh`, `stack-down.sh`)와 스택별 대역 선언(`uid-ranges.yaml`) |
| `harness/` | 실제 스택에서 신청 생명주기 전 사례를 돌리는 E2E 시험과 측정 도구 |
| `pvc-image-chart/` | 사용자 이미지 저장소 PVC 차트(현재 운영 스택은 쓰지 않음) |

## 5. 배포 위치

같은 코드를 네 스택에 띄운다. 스택마다 네임스페이스, UID 대역, 포트 대역이 다르다.

| 스택 | 네임스페이스 | 용도 | 실행 방식 |
|------|------|------|------|
| operation | `ailab-operation` | **실제 사용자가 쓰는 운영** | `baseline` |
| baseline | `ailab-baseline` | 실험 | `baseline` |
| noprobe | `ailab-noprobe` | 실험 | `noprobe` |
| full | `ailab-full` | 실험 | `full` |

운영 config-server는 `ailab-operation` 네임스페이스의 Helm 릴리스 `config-server-operation`이고, API Service는 `containerssh-config-service`다. admin_be는 클러스터 안 주소로 부른다. 구 운영 네임스페이스 `ailab-infra`는 2026-09-15에 내려 두었고, 스택 배포가 아직 그 안의 SSH 키 Secret과 Helm 값을 원본으로 읽는다.

실행 방식과 스택별 대역은 [시스템 아키텍처](design/시스템-아키텍처.md), 배포 절차는 [운영 매뉴얼](operations/운영-매뉴얼.md)에 있다. 전용 DB 구조는 [데이터베이스](design/데이터베이스.md)에서 본다.
