# 브랜치·배포 규칙

admin_fe·admin_be·admin_infra·admin_infra-proposed 네 저장소가 이 규칙 하나를 쓴다. 각 저장소 README의
"브랜치·배포 규칙" 절은 이 문서의 요약이다.

## 한 줄 요약

**브랜치는 `main` 하나. 작업 브랜치 → PR(CI 통과) → `main`에 squash 병합. 운영에는 네 저장소에 같은 이름으로 찍은
릴리스 태그만 올린다.**

## 1. 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `main` | 유일한 장기 브랜치. 항상 테스트가 통과하는 상태를 유지한다 |
| `<커밋 타입>/v<버전>-<짧은 설명>` | 작업 브랜치. `main`에서 따서 PR로 돌아온다 |

- 커밋 타입은 [Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/)와 같다:
  `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`.
- 버전은 개발 계획 버전이다(v2.0 제어기, v3.0 결과 확인, v4.0 재시도·이어하기, v5~6 접근 시험). 여러 저장소에 걸친
  같은 작업은 브랜치 이름을 맞춘다.
- 이슈 번호는 브랜치 이름에 넣지 않고 커밋 메시지·PR 제목에 남긴다.
- PR을 연 뒤에는 브랜치 이름을 바꾸지 않는다(GitHub가 그 PR을 닫는다).
- 예: `feat/v2.0-baseline-mode`, `fix/v3.0-returning-user-uid`, `docs/v3.0-branch-rules`

## 2. PR과 병합

- 대상은 항상 `main`이다.
- 병합은 squash만 쓴다. 커밋 메시지는 Conventional Commits 형식(`fix: …`)으로 쓴다.
- CI(각 저장소 `.github/workflows/ci.yml`)가 통과해야 병합한다.

| 저장소 | CI가 하는 일 |
| --- | --- |
| admin_be | `./gradlew test` (H2 메모리 DB, 가짜 설정값) |
| admin_fe | `pnpm install --frozen-lockfile` · lint(오류만 실패) · build |
| admin_infra | actionlint(워크플로 정의 검사, shellcheck 포함) |
| admin_infra-proposed | `pytest config-server` · `pytest harness` (가상 계층) |

- 세 저장소 모두 공개 저장소다. 워크플로 로그에 인프라 주소·계정 이름·설정값을 출력하지 않는다.

## 3. 배포

어느 저장소에도 push로 도는 배포가 없다. 배포는 admin_infra의 **Deploy Proposed Stack** 워크플로 하나로만 한다.

| 대상 | 넣는 코드 |
| --- | --- |
| 실험 스택(`baseline`·`noprobe`·`full`) | `main` 또는 시험할 작업 브랜치 (기본값 `main`) |
| 운영(`operation`) | 릴리스 태그 `vX.Y.Z`만. `ref`·`fe_ref`·`be_ref`가 모두 같은 태그여야 하고, 워크플로의 guard 작업이 아니면 막는다 |

## 4. 릴리스

1. 네 저장소의 `main`이 CI를 통과한 상태인지 확인한다.
2. 네 저장소 `main`에 같은 태그를 찍는다. 버전은 `v<개발 계획 버전>.<패치>` (예: `v3.0.0`, `v3.0.1`).
   ```bash
   git tag -a v3.0.1 -m "v3.0.1" origin/main && git push origin v3.0.1
   ```
3. 그 태그로 운영을 배포한다.
   ```bash
   gh workflow run deploy-proposed-stack.yaml -R CSID-DGU/admin_infra \
     -f stack=operation -f ref=v3.0.1 -f fe_ref=v3.0.1 -f be_ref=v3.0.1
   ```
4. 운영에 무엇이 떠 있는지는 태그 하나로 말할 수 있다. 되돌릴 때는 이전 태그로 같은 명령을 다시 돌린다.

## 5. 2026-09-26 전환 기록

예전에는 저장소마다 달랐다(admin_be·admin_infra·admin_infra-proposed는 `develop`+`main`, admin_fe는 `main`만).
실험 스택은 develop을 쓰고 운영은 저장소마다 develop이나 main을 썼다. `main`에 push하면 이미 꺼진 구 운영으로
배포하는 워크플로도 남아 있었다. 두 장기 브랜치는 서로 어긋났다(develop이 앞서거나 뒤처짐).

- 구 운영 배포 워크플로(admin_be `deploy.yml`, admin_infra·admin_infra-proposed `deploy-config-server.yaml`)를 지웠다.
- admin_be·admin_infra: 옛 `main`을 `legacy-main` 태그로 보존하고, `develop`을 `main`으로 이름을 바꿨다.
  옛 main의 내용은 develop에 모두 들어 있었다.
- admin_infra-proposed: `main`을 `develop` 끝으로 fast-forward하고 `develop`을 지웠다.

로컬 저장소에서 할 일:

```bash
git fetch origin --prune --tags
git switch main 2>/dev/null || git switch -c main origin/main
git branch -u origin/main main
git reset --keep origin/main     # 로컬 main이 옛 main을 가리키면
git branch -d develop            # 병합된 로컬 develop 정리
```
